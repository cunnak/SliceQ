# SliceQ v0.1.2

**建议所有 v0.1.1 用户升级。** 这个版本修掉了一个会让分析**完全白跑**的缺陷。

---

## 🔴 严重：跑完显示「0 个切片段」，而且提示点不开

**现象**：拿一段 84 分钟的录像跑分析，进度正常走完，
结果显示「完成：0 个切片段　⚠️ 2 条提示」——
但那 2 条提示**点不开**，不知道发生了什么。

**根因**：三个缺陷叠加。

1. **粗筛把候选段给得太长**。提示词没约束时长，模型把"这一段在讲什么"的
   摘要窗口当成了高光候选，单段最长到 10 分钟。
2. **候选被无限合并**。相邻候选（间隔 < 8 秒）会被合并成一段，而**没有长度上限**——
   实测把 10 个首尾相接的候选并成了**一个 20 分钟的巨块**。
3. **分析副本按固定码率切，从不看体积**。这个 20 分钟的副本编码出来是
   **90.6 MB**，而接口对单次提交有硬上限 ⇒ **超限 6.3 倍** ⇒
   两个候选**都在发出请求之前就被拒绝** ⇒ `clip` 表 0 行。

**为什么提示点不开**：失败原因只存在内存里，界面只显示了个数字；
日志里也一个字没有（分析流水线原先完全没有日志）。
进程一退出，原因就永远消失了。

### 修了什么

| 层 | 改动 |
|---|---|
| 候选长度 | 单段上限 **180 秒**；合并超限就切开，且切分**不留碎片**（余量不足 20 秒就并进尾块） |
| 提示词 | 明确要求"每段 20~120 秒、挑一个具体的高光瞬间"，并给了正反例 |
| 副本体积 | 按 **720p → 480p → 360p → 240p** 逐档自动下调，取第一个能塞进通道上限的档位；降到最低档仍超才缩短时长，并**如实告知** |
| 旧文件 | 已经存在但**超限**的旧副本会**自动重切** —— 否则你重跑多少次都还是同一个失败 |
| 提示可见 | 「⚠️ N 条提示」变成**可以点开**的按钮，显示全文、可复制；内容**存在数据库里**，重开程序、切走再回来都还在 |
| 日志 | 分析流水线补上日志：阶段、候选规模、**每个副本的规格**、**每次精析失败的原因** |

### 验证

用**你那次失败时的真实缓存**复跑：

```
原始 24 个候选（40~600 秒）
→ 修复后合并成 26 段，最长 185 秒（修复前：1 段 1200 秒）
→ 副本规格 360p/280kbps，205~240 秒 → 8.7~10.1 MB（上限 12.9 MB）
→ 真切实切 240 秒 @ 360p：实测 10.17 MB，估算 10.14 MB（偏差 +0.3%）
→ base64 14,216,320 字符 < 上限 20,000,000 ✅
```

新增回归自测 **55 项**（`candidate_length` 28 + `run_hints` 27），
其中包含**对照组**：旧逻辑必须能复现"1200 秒巨块"和"92MB 副本"——
否则这个测试等于没有牙。改动涉及的全部自测通过，无回归。

## 另外

- `clips_page` 出错时用 `print(detail)` 输出详情 —— 而打包版没有控制台，
  `print` 等于**把错误写进空气**。已改为写日志（同类问题本项目第二次犯）。
- 数据库 schema 升到 **v6**（自动迁移，不影响已有任务）。

## 你的老任务怎么办

**直接重开程序，点「重新分析」。**

- **转录会复用**（中间产物还在），不会重跑那几十分钟
- **粗筛也复用缓存**（0 次模型调用、0 花费）
- 但候选会按新规则重新合并（段数可能变多，每段明显变短）
- 那个 90 MB 的旧副本会被识别为超限并**自动重切**

⚠️ 候选变多意味着精析调用次数变多。如果超出你在启动时设的花费上限，
程序会**停下来问你** —— 那是设计里的成本闸门，不是故障。

## 升级方式

**单文件，直接替换即可。** 配置、API Key、模型缓存、历史导出都在
`%APPDATA%\SliceQ\`，**与 exe 放在哪里无关**，升级不会丢。
