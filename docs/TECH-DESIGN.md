> **🔴 v1.23 关键变更（真机验收后续：修一个 P0 缺陷 + R20 定论）**：
> 1. **🔴 修复 P0：OTIO 缺音频轨 ⇒ 达芬奇里没声音。**
>    §6.4 的甲方案数据结构原先只写 `1 Video Track`，达芬奇会自己建一条音频轨
>    但**是空的**，且**不会**从视频片段推断出音频。
>    ⇒ 改为 **Video Track + Audio Track 两条轨**，切点逐段一致，各建独立 Clip 对象。
>    （同一个 Clip 对象 append 到两条轨会互相覆盖 `range_in_parent`，不报错但位置错乱。）
> 2. **✅ R20 定论：原结论方向正确，但缺一个前提条件。**
>    用户确认上次**没有**手动改过起始时间码 ⇒ "项目属性论"被否证
>    ⇒ **达芬奇确实会采用 OTIO 的 `global_start_time`，但只在 OTIO 的 rate
>    与达芬奇项目帧率一致时才生效**；不一致时回退到项目默认的 `01:00:00:00`。
>    ⇒ **解法**：①（首选）新建项目时把时间线帧率设为素材帧率；
>      ②（兜底）手动把起始时间码改成 `00:00:00:00`。两条都已写进 `导入说明.txt`。
>    ⇒ **不能靠改 OTIO 的 rate 绕过** —— rate 必须写素材真实帧率（见第 3 条）。
> 3. **🔴 新发现：SRT 直接拖进达芬奇会整体提前约 0.54 秒。**
>    实测 32 条全部偏移 13 帧（恒定），根因是拖拽让达芬奇从时间线第 0 帧开始排列、
>    **丢掉首条字幕的起始偏移**。正确做法是"按时间码插入"。
>    ⚠️ 这**不是** R20（不是偏 1 小时）—— 说明达芬奇的**基准是对的**，问题在插入方式。
> 4. 自测 `selftest_exporter`：**73 → 83 项**（新增 10 项覆盖音频轨与说明文案）。

> **⚠️ v1.19 关键变更（数据模型升至 v5：补外键）**：

> **⚠️ v1.15 关键变更（阶段 4-C：批量并发）**：
> 1. **新增 `concurrency.py`**：粗筛/精析并发的统一实现（§5.3）。
>    ⚠️ **必须"窗口化提交"** —— 一次性把 N 个任务全提交给线程池，
>    会让 `should_cancel` 只在开头生效一次，**精析的成本闸门因此彻底失效**。
> 2. **回调必须在调用线程执行** —— 成本累计/进度/落库都在回调里；
>    放进工作线程就要处处加锁，而"漏加一处"表现为"钱偶尔少算"。
> 3. **默认串行**：并发会同时发多个请求，更容易撞限流。
> 4. **字幕默认配色改为白字黑边**（原为设计稿的亮绿）。
>    改常量不够，还要重置磁盘预设（`load_preset` 优先读磁盘）。

## 1. 总架构

桌面单机应用，无自建服务器。视频文件不出本地；只有"分析副本"（抽帧/音频/低码率片段）经用户自带的百炼 API key 上行。模型负责理解与决策，FFmpeg 负责一切音视频执行。

>
> - **通道 A · 官方 DashScope SDK**：视频走**本地文件路径直传**，副本上限 100MB。

>
> 两条通道都**不需要 OSS、不需要上传**，隐私承诺（视频不出本地）在两条路径上都成立。

## 2. 两级分析流水线（核心设计）

**要解决的问题**：直播录像通常 2~6 小时，模型单次音视频输入上限约 2 小时，且全量喂视频成本不可接受。

**解法：官方 Agentic 思路的应用层复现——先粗筛、再精析。**

### 2.1 粗筛级（转录本地免费、覆盖全片）

1. FFmpeg 从原视频提取 16kHz 单声道音频，按 30~60 分钟分段。
2. **转录走 asr.py 抽象层**（零成本优先）：
   - **首选（默认）：FFmpeg 内置 `whisper` 滤镜**（whisper.cpp 集成）
     - 零新增依赖（FFmpeg 本就要分发）、零 API 成本、零合规风险
     - **静音预切除**：先用 `silencedetect` 扫出静音，只把语音区间拼成连续音频喂给 whisper
     - ~~设 `vad_model` 启用静音检测、跳过无声段落~~ —— **实测无效，已弃用**（见 §2.4.1）
     - `format=json` 直出（⚠️ 实为 **JSONL**，每行一个对象；时间戳单位**毫秒**）；
       `language=zh` 显式指定避免误判
     - 模型经 hf-mirror.com 镜像下载（HuggingFace 直连在国内不通，实测静默失败）
   - **可选（"高精度字幕"开关）：faster-whisper** —— 提供词级时间戳，代价是引入 Python ASR 依赖链
   - **兜底：Qwen 音频理解** —— 前两者均不可用时（+¥0.5/条，明示用户）
   - ~~必剪/剪映私有接口~~ —— **已放弃**（合规灰度 + 接口不可控，收益已被 ffmpeg 路线完全覆盖）
3. **粗筛信号 = 文本 + 抽帧**（2026-09-25 决策）：
   - **文本**：转录文本按时间窗送入模型做语义粗判（纯文本调用，极便宜：
     "这段有没有符合需求的苗头？"）
   - **抽帧（拼贴，不是逐帧）**：每窗抽 16 帧拼成**一张联系表**后再送模型。
     逐帧送的话 3 小时要 360~1080 次图片调用；拼贴后覆盖全片只需约 20 张。
     **这是粗筛能便宜下来的关键。** 拼贴按"从左到右、从上到下"对应窗口内均匀采样的画面，
     这个顺序必须写进提示词，否则模型无从判断时间位置。
   - **弹幕：v1 不做**（需要额外的抓取通道，且素材来源不保证有弹幕）
4. **幻觉治理**：转录文本必须先过三层过滤再进粗筛。
   **否则幻觉会被当成真实文本参与语义打分，把没语音的片段推成候选，白烧精析的钱。**
   详见 §2.4。
5. 输出：**候选时间段列表**（粒度 1~5 分钟）。
   硬性成本控制阀：候选段总时长 ≤ **max(全片时长 × 20%, 120 秒)**。
   ⚠️ 那个 **120 秒的绝对下限不能省**：纯按比例会毁掉短片 ——
   12 秒素材 × 20% = 2.4 秒预算，任何合理候选（几秒到几十秒）都会被砍光，
   用户看到的是"0 个候选"。
   **比例是长视频的约束，绝对下限是短视频的保护。**

### 2.2 精析级（贵、只打候选点）

1. 每个候选时间段前后各扩 30 秒缓冲，FFmpeg 切出低码率"分析副本"。
   **副本压制参数按 transport 分档**（这是阶段 0.5 实测后新增的约束）：

   | Transport | 副本上限 | 参考压制参数 | 单段可承载时长（估算） |
   |---|---|---|---|
   | A · 官方 SDK（本地路径） | 100MB | 720p / 1Mbps | ~13 分钟 |
   | B · HTTP 兼容（base64） | **原始 ≤15MB** | 480p / 0.5Mbps | ~4 分钟 |
   | B · HTTP 兼容（更保守） | 原始 ≤15MB | 360p / 0.3Mbps | ~6.5 分钟 |

   > 成本不随"分段数"变化（token 按秒计，见 §2.3），所以**通道 B 下宁可把候选段切细**，也不要为了塞进一次请求而牺牲画质。
2. 副本送模型（音视频完整输入）：输出精确起止（秒级）、高光类型、评分（0-100）、一句话描述、标题素材。
3. 汇总为候选清单写库，UI 展示。

### 2.3 成本估算（v1.3：实测校准，不再是推算）

**全模态同价**：输入 ¥0.8/百万 token、缓存命中 ¥0.1/百万 token、输出 ¥2.7/百万 token。

**实测基准（阶段 0.5）**：视频输入的 token 消耗呈干净的线性关系 —— **≈228 token / 秒视频**，五档体积实测一致，**与文件体积无关**（1MB 与 10.8MB 的同长度视频 token 相同）。

| 环节 | 量级 | 成本 |
|---|---|---|
| 3 小时音频转录 | **FFmpeg 内置 whisper（本地）** | **¥0** |
| 语义粗判（纯文本） | 3h 转录约 4 万 token 分窗 | ¥0.03 ~ 0.10 |
| 抽帧粗判 | ~200 帧 | ≤ ¥0.05 |
| **精析（36 分钟 = 2,160 秒候选段）** | 2,160 s × 228 = **492,480 token** × ¥0.8/M | **¥0.39** |
| 精析输出（关思考） | 按 120s/段 = 18 次调用 × ~200 token × ¥2.7/M | ¥0.01 |
| 断句/文案（纯文本） | 候选段字幕 | ≤ ¥0.05 |
| **合计** | | **≈¥0.45 ~ 0.55 / 3 小时录像** |

> 对照：v1.1 估 ¥1~2.5 → v1.2 估 ¥0.3~1.5 → **v1.3 实测 ¥0.45~0.55**。PRD KR3（≤¥1）宽裕达标，**余量约一倍**。
>
> **待验证的优化杠杆**：分析副本降低 fps（15→5）可能减少模型采样帧数，直接压缩 token。阶段 2 实测确认。
>
> 降级情形：faster-whisper 本地（¥0，耗时换）→ Qwen 转录（+¥0.5，需用户确认）。

### 2.4.5 判重门槛分档（v1.18 修正）

**实测暴露的缺口**（2026-09-26，90s 真实素材）：

    1. [  5.9] 感谢观看
    2. [ 17.7] 感谢观看
    3. [ 20.6] 感谢观看
    ...
    17. [ 64.8] 优优独播剧场——YoYo Television Series Exclusive

三层防线**一处都没拦住**，原因具体到有点荒诞：

| 缺口 | 原因 |
|---|---|
| `感谢观看` 重复 5 次 | `_REPEAT_MIN_LEN = 8` ⇒ 4 字**根本不参与判重** |
| `优优独播剧场…` | 特征词表没这个模板（电视台用语）|
| 词表有 `谢谢观看` 没有 `感谢观看` | 一个字之差 |

**修法**：门槛分档 + 词表补充。

    长句（≥8 字）：重复 3 次即判
    短句（4~7 字）：重复 5 次才判     ← 新增档
    极短（<4 字）：一律不判

短句档不能直接套 3 次 —— 真实口语里"我知道了"重复 3 次完全可能。
抬到 5 次后，"真实讲话不会逐字重复 5 遍"这个客观判据仍然成立。

### ⚠️ 为什么不把 `感谢观看` 加进特征词表

主播下播时**真的会**说"感谢观看"。按词剔除会误杀真实内容。

而"重复 5 次"是**客观判据**，不是猜。所以短幻觉走判重、不走词表。

> 这条原则来自 `looks_like_hallucination()` 的 docstring：
> **"宁可漏判，不要误杀真实内容。"**
> 判重是"删内容"的操作，删错了**不会有人发现**（转录少了几句，谁看得出来）。
> 所以每一项都要有可复现的判据，而不是"看起来像"。

**实测效果**：同一段素材，粗筛候选 **0 条 → 1 条**，
转录段数 28 → 22。

> 注意这不只是"少几句废话"：**粗筛是基于转录文本打分的**。
> 文本被幻觉污染时它会判"无价值"，用户因此拿不到本该有的切片。

验证：`selftest_hallucination.py`（26 项）**双向验证** ——
既查"该清的清了"，也查"不该清的一条都不能少"
（极短应答词、真实口语 3 次重复、正常内容零剔除）。

### 2.4 幻觉治理（三层防线）

> 完整证据链见 `reports/STAGE2-PRE-HALLUCINATION-CONTROL.md`

#### 2.4.1 为什么不用 `vad_model`（已证伪）

**现象**：whisper 在无语音片段上会吐出模板文案
（`請不吝點贊 訂閱 轉發 打賞支持明鏡與點點欄目`、`謝謝收看`、`(字幕:J Chong)`），
语意通顺，会被粗筛当成真实文本参与打分。

**原方案**：设 `vad_model` 让它跳过非语音。**实测无效。**

| 判据 | 结果 |
|---|---|
| 参数是否生效 | ✅ 生效（传非法模型路径会报 `failed to open VAD model`） |
| **30 秒纯数字静音** | **无 VAD 出 11 段幻觉；有 VAD @0.4 也是 11 段，文本完全相同** |
| 阈值扫描 0.3 / 0.4 / 0.5 | 幻觉 23 / 23 / 22 段（几乎不变） |
| 耗时 | **12s → 46~48s（×4）** |

**根因（源码 `libavfilter/af_whisper.c` 的 `filter_frame()`）**：
VAD 只用来判断**何时触发转录**，而转录范围是 `run_transcription(ctx, frame, end_pos)`
—— 从 **buffer 第 0 个样本** 开始。若 buffer 是 `[静音 53s][语音 30s]`，
前面 53 秒静音**原封不动**被送进 whisper。

官方文档措辞可印证：VAD 是 *used to **fragment** the audio queue*（分片），
不是 *filter out*（滤除）。

⇒ **`vad_model` 不采用。** `asr.py` 已移除相关参数。

#### 2.4.2 三层防线与实测效果

```
① 静音预切除    silencedetect 扫静音 → 取补集 → aselect 拼成连续音频 → 只喂语音
② 逐字重复剔除  同一句重复 ≥3 次 → 全丢（真实讲话不会这样）
③ 特征词剔除    感谢订阅 / 字幕制作 / 小铃铛 等模板文案
```

实测（140s 素材，含 53.6s 静音）：

| 层 | 段数 | 幻觉 |
|---|---|---|
| 0 · 不处理 | 51 | **23** |
| 1 · + 静音预切除 | 34 | **6** |
| 2 · + 重复文本剔除 | 29 | **1** |
| 3 · + 特征词剔除 | 28 | **0** |

`silencedetect` 扫描成本极低：140s 音频 **0.2s**（2.5 小时约 5s），比 VAD 的推理便宜几个数量级。

#### 2.4.3 实现约束（都在 `asr.py` 里落成注释）

1. **空区间必须特判**：`aselect=''` **不报错、不警告，直接输出整段原音频** ——
   等于静音一条没切而毫无迹象。空区间要显式返回 0。
2. **整片静音要跳过**，不要交给 whisper。
3. **判重必须全局做**，不能按分片（重复会跨片出现）。
4. **判重必须设长度门槛**（`≥8 字`）：短应答词（"好"、"啊"、"对"）重复是正常的，判重会误杀。
5. **切点 padding 取 0.25s**：既避免切断词边界，残留静音又短到不足以诱发幻觉。
6. **时间轴映射是必需配套**：静音切除会改变时间轴，必须映射回原轴。
   **漏了不报错，但字幕整体错位。**

#### 2.4.4 已知边界（**不是万能药**）

| 场景 | 覆盖 |
|---|---|
| 真静音（无任何声音） | ✅ |
| **有 BGM 但无人声** | ❌ **silencedetect 抓不到**（不是静音），仍可能幻觉 |
| 语音中的短暂停顿（<2s） | ❌ 不切（也**不应该**切，会断句） |
| 语法通顺、语义无关的凭空句子 | ❌ 特征词抓不到（只能靠重复判重碰运气） |

第二行是最大盲区：直播开场等待、中途放片等"长时间只有音乐"的段落会有残留。
**v1 接受该边界，v2 再评估引入真正的语音检测。**

### 2.5 成本阀的用户呈现

**核心判断：成本阀的功能不是"省钱"，是"消除不确定性"。**

3 小时录像实测 ≈¥0.45~0.55，对做切片的人不构成成本压力。
用户真正的不安来自：事前不知道会花多少、事中不知道会不会失控、事后不知道值不值。

#### 2.5.1 设计原则

1. **用钱说话，不用 token。** 切片 man 不看 token。
   金额放主位，token 数放「详情」折叠区（留给想核算的人）。
2. **预估给上限，不给典型值。**
   预估 ¥0.5 实花 ¥0.3 → 用户觉得赚；预估 ¥0.3 实花 ¥0.5 → 用户觉得被骗。
   **预期管理要往差的方向偏。**
3. **确认点只有一个，且放在"信息最充分、钱还没花"的时刻。**
4. **明说"不精析也有用"。** 粗筛产出的候选清单（时间点 + 转录摘要）本身就能直接拿来剪 ——
   `[先看清单]` 是正当选项，不是"取消"。这一条最能降低心理压力：
   用户知道自己在选，而不是被迫花钱。

#### 2.5.2 确认点为什么设在"粗筛完成、精析开始前"

3 小时录像（候选段 20% 上限）的成本分布：

| 环节 | 成本 | 占比 |
|---|---|---|
| 转录（本地） | ¥0 | 0% |
| 粗筛（语义 + 抽帧） | ¥0.08~0.15 | 18% |
| **精析** | **¥0.39** | **72%** |
| 文案 | ¥0.05 | 9% |

精析占七成以上，**而它的精确报价只有粗筛完成后才能算**（要知道候选段总时长）。
⇒ 那个时刻同时满足"信息最充分"和"钱还没花"，是唯一值得停顿的地方。

#### 2.5.3 三处可见性

| 时点 | 显示内容 | 是否打断 |
|---|---|---|
| ① 点「开始分析」后 | 本轮**花费上限**（按候选段打满 20% 估算）+ 预计时长 | 否 |
| ② **粗筛完成** | 候选段数 + 总时长 + 精析**报价** + 硬上限<br>`[开始精析]` / `[先看清单，稍后再说]` | **是（唯一）** |
| ③ 精析完成后 | **实际花费** + 预估对比 + 累计花费 + "以百炼账单为准" | 否 |

#### 2.5.4 实现约束

- **实际花费按 API 返回的 `usage` 精确计算**；预估只能按
  `时长 × 228 token/秒 × 单价` 推算。**两者并列显示**（预估 ¥0.31 / 实际 ¥0.28）——
  这是长期信任的来源。
- **必须注明「以百炼账单为准」**：BYOK 下真实扣费在阿里云后台，应用内是估算。
  不说明清楚，用户发现对不上会失去信任。
- **提供「总是自动继续」开关**：高频用户不想每次被问，可关闭确认点（设置页可改回）。
- **硬上限默认 ¥2**：超限时**暂停并询问**。它只在异常时起作用
  （如某段音频异常长导致 token 爆炸），正常使用永远碰不到。
- **重试/重跑要累计**：失败重试时已消耗的部分如实累加，不重复计算。
- **术语**：界面用「花费上限」，**不要用「成本控制阀」**。

#### 2.5.5 候选段 20% 上限 —— 对用户翻译成「筛选强度」

这条硬阀不该呈现为"限制"，而应呈现为**用户可理解的取舍档位**：

| 档位 | 候选段上限 | 3 小时录像约 |
|---|---|---|
| 轻 | 10% | ¥0.28 |
| **标准（默认）** | **20%** | **¥0.53** |
| 广 | 35% | ¥0.88 |

含义从"隐藏的技术限制"变成：**"我最多精读多少比例的内容，为此付多少钱。"**

### 2.6 ★ 粗筛失败的报错分层（v1.20）

粗筛"0 个候选"有三种成因，**必须分开报**：

| 成因 | 该怎么报 | 用户该做什么 |
|---|---|---|
| 全部窗口调用失败（`windows_failed>0 and windows_done==0`）| **抛 `PipelineError`**，附第一条原始原因，并明说"这不是素材的问题" | 修配置（key / 端点 / 网络）|
| 部分窗口失败 | 继续跑，但提示"N 个窗口没能分析成功，漏掉的内容可能在其中" | 先重跑 |
| 真的没有 | 提示可调需求描述 / 筛选强度 | 调需求 |

**为什么必须分开**：实测（2026-09-27）端点被配成需要未安装的 `dashscope`
包的通道 ⇒ 唯一窗口失败 ⇒ 候选 0 ⇒ 用户看到的是

    "没有找到符合条件的候选段。可以试试：① 把需求描述写得更具体；
     ② 调高「筛选强度」档位；③ 换一段素材验证。"

这段话**读起来通顺、语气也友好**，但三条建议全在引导他改无关的东西。
用户会去改需求、换素材，白折腾一圈，而且**不会意识到自己被误导了**。

> 教训：`degraded` 列表里其实**有**真实原因，但它被"0 候选"的
> 提示话术盖住了。**错误信息不能把病因替换成一个不存在的问题。**
> 判据见 `selftest_fault_injection.py` 的 F 组 ——
> 它断言的不只是"抛了可读错误"，还包括
> **该说的说到了（`expect_in`）、不该说的没说（`expect_not_in`）**。

## 3. 模型接入（analyzer.py）

### 3.1 Transport 设计（v1.3 重构：本地路径是 SDK 能力，不是协议能力）

- **模型**：`qwen3.8-omni-flash`（阶段 0.5 已在真实端点实测跑通）
- **端点形态决定视频怎么送**——这是本节的核心结论，必须分成两条通道实现。

#### 通道 A：DashScope 官方 SDK（主通道）

| 项 | 值 |
|---|---|
| 依赖 | `dashscope` pip 包 |
| 视频输入 | ✅ **本地文件路径直传**（也可 base64 / 公网 URL） |
| 体积上限 | 本地路径 ≤ **100MB**；base64 官方限 10MB（原始须 <7MB） |
| 优点 | **无需 OSS、无需上传、无需公网 URL**；副本体积约束宽松 |
| 前提 | 用户持有阿里云百炼账号（新用户有 100 万 token 免费额度） |

官方文件传入规格（供对照）：

| 文件类型 | 规格 | DashScope SDK | OpenAI 兼容 / HTTP |
|---|---|---|---|
| 视频 | > 100MB | 仅公网 URL | 仅公网 URL |
| 视频 | 7MB ~ 100MB | ✅ **可传本地路径** | ❌ 仅公网 URL |
| 视频 | < 7MB | ✅ 可传本地路径 | 可 Base64 |

#### 通道 B：OpenAI 兼容 HTTP（兼容通道，含中转站）

| 项 | 值 |
|---|---|
| 依赖 | `requests` |
| 视频输入 | ❌ **无本地路径**（服务端物理上访问不到用户磁盘）；✅ base64 data URI；✅ 公网 URL |
| **体积上限** | **base64 字符串 ≤ 28,000,000 字符**（实测撞墙值，见下）；对应原始文件 ≈ **20.99MB** |
| **建议工程上限** | **原始 ≤ 15MB / base64 ≤ 20MB**（留 30% 余量） |
| 报错特征 | `String value length (xxx) exceeds the maximum allowed (28000000, from StreamReadConstraints.getMaxStringLength())` |
| 优点 | 门槛低（兼容端点遍地）；仍是"免上传"——base64 直接内联，不需要 OSS |
| 缺点 | 副本必须压得很小，反向约束"候选段粒度"与"副本码率" |

> ⚠️ **上限来源辨析**：28,000,000 字符这个限制来自**中转站网关的 Java Jackson 反序列化保护**，**不是模型能力**。官方文档称 base64 单文件上限 10MB——实测中转站反而更宽松（13.78MB base64 通过）。**不要用官方文档的 7MB 去做设计，以实际端点实测为准。**

#### 实现要求

```python
# analyzer.py 的 transport 抽象
class Transport(Protocol):
    def analyze(self, video_path: str, prompt: str, ...) -> Result: ...

class DashScopeTransport:   # 通道 A：本地路径直传
    MAX_LOCAL_BYTES = 100 * 1024 * 1024
class HTTPTransport:        # 通道 B：base64 内联
    MAX_B64_CHARS = 20_000_000      # 保守值，硬上限 28_000_000
```

启动时按用户填的 base_url 自动判定通道（含 `dashscope.aliyuncs.com` → A；否则 → B），并允许手动覆盖。**两条通道的副本压制参数不同**（见 §2.2）。

- **鉴权**：BYOK。key 存 `%APPDATA%/SliceQ/config.json`（Windows DPAPI 加密）。同时存 `base_url`（默认官方端点，可填中转站）。

### 3.2 已确认的模型边界（阶段 0 查证）

| 项 | 值 |
|---|---|
| 视频单请求上限 | **2 小时 / 2GB**（URL 方式）；本地路径方式单文件 ≤100MB |
| 音频单请求上限 | 3 小时 |
| 上下文 | ~1M token（实测上限约 991K） |
| 采样 | ≤15fps 可得稳定结果 |
| 视频时长范围 | 2 秒 ~ 2 小时（qwen3.8 系列） |
| 多视频 | 单请求最多 64 个 |
| 音频语言 | 113 种语言/方言 |
| 输出 | **仅文本**（不含语音生成） |
| 可用地域 | 北京、新加坡、中国香港、东京、法兰克福、弗吉尼亚 |
| 免费额度 | 100 万 token（仅北京地域，90 天内有效） |

> ⏳ **待实测（需 key）**：qwen3.8-omni 系列对传入视频的**音轨理解能力**。VL 系列文档明确"不支持对视频文件的音频进行理解"，omni 系列的卖点正是音视频联合理解，应不适用——但必须实测确认，否则"用音量/情绪判断高光"的整条路径要改。

### 3.3 提示词骨架（内容画像注入点）

```
[系统] 你是直播切片分析师。用户的内容画像：{profile_prompt}
[用户] 这是直播录像的第 {i}/{n} 段（时间偏移 {offset}）。
       用户需求：{user_prompt}
       任务：找出符合需求的候选时间段，JSON 数组输出：
       [{"start": 秒, "end": 秒, "hint": "理由", "confidence": 0-100}]
```

- **三个内置模板**（填入即画像提示词，用户可改）：
  - 游戏：击杀/超神/翻盘/下饭操作，关注音量突增、击杀播报、弹幕关键词
  - 娱乐：爆梗/破防/名场面/礼物特效，关注情绪爆发与互动峰值
  - 通用：音量、画面变化、语速突变的综合异常检测
- **思考参数（v1.3 实测新增）**：默认 `enable_thinking: false` —— 精析要的是结构化定位，不需要长推理。实测默认开启思考时，**65%~75% 的输出预算被 reasoning 吃掉**（如 completion=1197 中 reasoning=891），且耗时不随输入线性。
  - 参数做成**三态可配**：`auto`（不发送）/ `off`（发送 false）/ `on`（发送 true）
  - 收到 400/422 时**自动摘除该参数重试**（这是 Qwen/DashScope 系私有参数，不是所有端点都认）
  - `max_tokens` **不得低于 800**，给结构化 JSON 输出留余量
- **空返回自检（必做）**：若出现 `正文为空 且 usage.completion_tokens_details.reasoning_tokens > 0`，说明思考把预算吃光了 → 自动改 `enable_thinking:false` 重试一次，**并把降级事件上报到 UI**（静默降级等于隐瞒）。
- **容错**：429/5xx 指数退避重试（最多 5 次）；单段失败不阻塞全局，标记后可重跑；所有请求/响应落日志（成本核算依据），逐条记录 token 用量以便回填 §2.3。

## 4.5 字幕处理管线（subtitle.py）

```
转录（句级或词级时间戳） → LLM 语义断句 → 校正 → （可选）翻译
   → ★ 时间轴重映射（源时间轴 → 新时间线时间轴）→ SRT → 交 editor.py 烧录
```

| 环节 | 设计 |
|---|---|
| 时间戳来源 | **默认句级**（ffmpeg whisper 输出 `{start, end, text}`，毫秒）；勾选"高精度字幕"时切 faster-whisper 取词级 |
| 断句 | **默认路径**：LLM 按语义完整性切分，单条 5~20 字、不超 2 行，杜绝半句断裂；切分点时间戳由字数比例在句内**插值**（长句内误差约几十毫秒，人眼无感）。**词级路径**（可选）：直接取词边界对齐 |
| 校正 | 标点恢复、同音错别字修复、口语赘词（"那个""然后"）可选清理 |
| ~~翻译-免费~~ | **❌ 已废弃（v1.14 实测）**。原设计"必应/谷歌网页接口，零成本质量够用"被推翻：Google 被墙、必应 401、LibreTranslate 403、MyMemory 质量不可用。详见 §4.5.1 |
| **翻译-精翻** | **唯一路径**。LLM 反思式：直译 → 对照原文审校 → 定稿，一次调用内完成。实测 **255 字 ¥0.0008**。MyMemory 仅作"没配 key 时"的兜底且必须告知质量降级 |
| **★ 时间轴重映射** | **甲方案必需**（v1.7 新增）。转录时间戳对齐**源视频绝对时间轴**；但成片是多个非连续高光片段的拼接，时间轴不同。必须按 §6.4.3 公式把源时间映射到新时间线时间。**editor.py 烧录与 SRT 导出必须共用同一映射函数** |
| 输出 | 单语 SRT / 双语 SRT（中文上行、译文下行）；烧录样式：中文大字号、译文小号 |

> **v1.7 新增**：时间轴重映射环节。**漏做不会报错，但字幕整体错位**——属"功能正常、结果全错"类缺陷（详见 §6.4.3）。

> **v1.2 修正**：v1.1 把"词级时间戳"写成管线前提，与 ffmpeg whisper 的句级输出冲突。现改为**句级为默认、词级为可选升级**——保住最轻的默认体验，不放弃精度上限。

### 4.5.1 为什么不用免费翻译通道（v1.14 实测）

| 通道 | 结果 |
|---|---|
| Google `translate_a/single` | ❌ `translate.googleapis.com` / `translate.google.com` **双双 ReadTimeout** |
| 必应 `ttranslatev3` | ❌ **HTTP 401 `{"ShowCaptcha":false}`** |
| 必应（带 IG/IID/AbuseParams） | ❌ 同样 401 —— 页面能取到 token，接口仍拒绝非浏览器会话 |
| LibreTranslate ×3 公共实例 | ❌ 全 403 / SSL 失败 |
| MyMemory | ✅ 通，但质量不可用（「在床路崎岖中流浪」→「wandering in the rugged bed road」）|
| 基线（必应首页 / GitHub） | ✅ 通 —— 排除了"整个网都不通" |

> 必应那条值得记住：**步骤看起来全对（页面 200、IG/IID/token 都拿到了），
> 接口依然 401。** 这类情况不要继续猜参数 —— 服务端在做会话/指纹校验，
> 客户端绕不过去，继续试只是浪费时间。

LLM 精翻实测成本：

| 方式 | 20 条 / 255 字 | 单字成本 |
|---|---|---|
| LLM 直翻 | ¥0.00066 | ¥0.0000026 |
| LLM 反思式精翻 | ¥0.00080 | ¥0.0000031 |

**1 分钟字幕 ≈ ¥0.0008。** 便宜到没必要为省它去接一个质量不可控的接口。

### 4.5.2 ★ 翻译必须逐行对应（高危）

字幕按行对应画面。模型**少输出一行**，从那一行起**所有字幕都会错开，
而且不产生任何报错** —— 与甲方案的"时间轴漏映射"同一类缺陷。

**三层防线**：

| 层 | 做法 |
|---|---|
| ① 提示词 | 显式编号，强调"输入几行就输出几行"。实测不写编号时模型会自行合并句子（20 条变 17 条）|
| ② 解析校验 | 条数必须 == 期望，否则返回 `None`。**编号超出 1..expect 一律判失败** —— 不能"过滤掉就完事"（多出来的一行是噪声还是"模型把两条拆成三条"，从文本上分不出来）|
| ③ 降级链 | 重试一次 → 仍不符则**拆成单条逐条翻译** → 单条也失败则该条**保留原文** |

**"保留原文"而不是丢弃**是关键：丢掉会让后面的行整体前移，那正是要避免的错位。

> 本条是"容错逻辑本身制造假象"的又一例：把越界编号当噪声过滤掉，
> 结果 `1.a/2.b/3.c`（期望 2 条）返回 `[a,b]`，**看上去完美**。
> 判断标准：这个容错是否**掩盖了不可区分的情况**。是，就不能容。

### 4.5.3 两个 transport 参数不要传混

`subtitle.build_for_clip()` 有两个：

    transport            —— 断句用（LLM 语义切分）
    translate_transport  —— 翻译用（填 cue.sub）

两者可以传同一个对象，但语义独立：断句可以关（`use_llm=False`）而翻译照做，反之亦然。
**传错不会报错，只会"没有译文"**（实测踩过：只传 `transport` 却开 `bilingual=True`）。

⚠️ 翻译发生在 **`remap_to_clip()` 之后** —— 只翻成片里真正会出现的字幕，
否则会把片段边界外、最终被丢掉的条目也翻一遍（白花钱）。

## 4.6 字幕样式系统（subtitle_style.py，v1.12 新增）

### 4.6.1 为什么是 ASS 而不是 SRT

样式面板要「主字幕」与「副字幕」的**字体、字号、字间距、颜色、边框颜色、
边框粗细全部独立可调**。SRT 做不到 ——
`subtitles=x.srt:force_style=...` 里的 `force_style` 是**全局覆盖**，
对文件里所有字幕统一生效；SRT 本身也不携带样式信息。

ASS 可以：`[V4+ Styles]` 里定义 `Main` / `Sub` 两套样式，
每条字幕按层选用，各自的字体/颜色/边框/垂直位置互不干扰。

> **SRT 仍然产出**，但定位变为「交付物」：给达芬奇导入、给其它软件加载
> （C 路线三件套之一）。它不承担样式。

### 4.6.2 四个必须记住的实现坑（均已实测）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | **颜色是 `&HAABBGGRR`，B 与 R 对调** | 写错不报错，只会颜色错（红蓝互换） | `rgb_to_ass()` 单一实现，带往返测试 |
| 2 | **滤镜参数里的 Windows 路径要双反斜杠转义** | `subtitles=C:/...` 报 `Unable to parse "original_size"` | 优先「相对路径 + cwd」；退路才是转义 |
| 3 | **字体缺失时 libass 静默 fallback** | 用户以为"改了没反应" | UI 层校验 + 明确提示替代字体 |
| 4 | **中文不会自动换行，会溢出被裁** | 首尾各少几个字，无任何警告 | `wrap_for_canvas()` 自己做分行 |

**第 4 条展开**：中文没有空格，libass 把整串当一个不可断的"词"，
放不下时不是换行而是溢出画布。实测 18 字字幕在 406px 宽、字号 42 的画面上
渲染成「维码过来叫我扫一下我付2」。

`wrap_for_canvas()` 的策略：**先算需要几行，再按行数均匀分配**；
均匀分配是"更好看"，**每行都不超宽是硬约束**（不满足则退回贪心分行）。
宁可多一行，也不能丢字。

### 4.6.3 垂直布局

```
下方那层：MarginV = 画布高 × 7%
上方那层：MarginV = 下方 MarginV + 下层行高 + 垂直间距
```

哪一层在下由「译文在上/下」开关决定。

> ⚠️ MarginV 必须按**画布高度比例**算，不能写死像素常量 ——
> 它在 ASS 里是相对 `PlayResY` 的，不同分辨率下同样的数值会得到不同的视觉位置。

**尺寸来源**：`ffmpeg_tools.probe_video_size()` 自己探测，
**并且要读旋转元数据**（竖屏直播常用 `rotate=90`，ffprobe 报的是编码尺寸，
不是用户看到的尺寸；用错会让字幕横竖颠倒）。
不接受调用方"猜一个尺寸"——实测踩过：按源片标称值传 720×1280，
而真实素材是 406×720，字幕全走样。

### 4.6.4 预设与预览

- 预设存 `%APPDATA%/SliceQ/styles/<名字>.json`；`default` 也可被用户改写
  （"我调完一关就丢"会被当 bug 报上来），并提供「恢复默认」还原出厂值
- **预览走完整渲染链路**：生成真 ASS → 交给真 libass → 出一张真帧。
  自己用 PIL/QPainter 画的话，换行、描边、字间距都会有细微差别 ——
  预览好看、成片不一样是最恼人的一类问题
- 防抖 280ms + 异步 + 序号校验（丢弃过期结果）

## 4.7 标题与简介生成（copywriter.py，v1.14 新增）

给每条候选生成 **3 条不同角度的标题 + 1 段发布简介**，一键复制。

| 项 | 设计 |
|---|---|
| 素材范围 | **只给这个片段说过的话**（按片段时间范围裁转录），不把整片丢给模型 |
| 标题 | 3 条，要求"角度不同"（说结论 / 说冲突 / 说场景）。实测只说"写三个标题"会得到三句同义的话 |
| 简介 | 1 段 60~110 字，可引用原话金句，但不许编造没有的内容 |
| 失败处理 | **逐条隔离**：这一条失败只影响这一条，不中断整批（与 `export_clips` 同样的取舍）|
| 成本 | 实测每条约 **¥0.001**，但仍**逐条记进流水**，与 pipeline 的成本可见性一致 |

> ⚠️ **只给片段内的转录**这一条很重要。把整片转录喂进去，
> 模型会拿别处的信息来写这个片段的标题 —— 而且**从结果上看不出来**。

## 5.3 并发（concurrency.py，v1.15 新增）

粗筛（按窗口）与精析（按候选）共用同一套并发语义。

| 约束 | 原因 |
|---|---|
| **回调在调用线程执行** | 成本累计/进度/落库都靠回调；放进工作线程就要处处加锁，而"漏加一处"表现为"钱偶尔少算"，几乎无法复现 |
| **窗口化提交**（保持 ≤workers 个在途，完成一个补一个）| 一次性全提交会让 `should_cancel` 只在开头生效一次 —— 而精析的**成本闸门**正做在这里。后果是**用户设的花费上限形同虚设** |
| `workers <= 1` 走独立串行路径 | 默认配置下与并发前行为一致，且可被直接对照验证 |
| 取消 = 不再提交新任务 | Python 无法硬中断线程；假装能只会制造半途状态 |

`pipeline.Options.concurrency` 与 `settings.concurrency` 默认均为 **1（串行）**。
界面在设置页「分析性能」里可调到 2~4，并注明"更容易触发服务端限流"。

**转录阶段固定串行** —— 实测证伪了并发收益（§5.6），
`concurrency` 设置只作用于粗筛/精析。

## 5. 剪辑执行（editor.py，全部 FFmpeg）

| 动作 | 命令骨架 | 注意 |
|---|---|---|
| 精确切片 | `ffmpeg -ss {a} -t {dur} -i in.mp4 -c:v libx264 -c:a aac out.mp4` | **实测时长偏差 0.000s**。`-ss`/`-t` 都放 `-i` 之前。<br>⚠️ 此处若烧字幕会带 cwd，**所有路径必须 `.resolve()`**（R27） |
| 快速切片 | `ffmpeg -ss {a} -t {dur} -i in.mp4 -c copy out.mp4` | **实测时长偏差仅 +0.10~0.15s**（旧文档写的 "±2s" 是错的），<br>且画面与源**逐像素一致**（PSNR = inf）。**不能烧字幕**（烧字幕必须重编码） |
| 合成多片段 | concat demuxer（同编码参数） | 重编码参数统一 |
| 硬字幕 | `subtitles=clip.srt:force_style='FontSize=22,Outline=2,OutlineColour=&H80000000'` | SRT 由 subtitle.py 生成；样式白字黑边居中 |
| 转场 | **单片段首尾 `fade` / `afade`**（乙方案下没有相邻片段，`xfade` 不适用） | 见 §5.2。`xfade` 仅留给未来可能的「合集模式」，且它要求两路输入分辨率**完全一致**，否则 `Conversion failed!` |
| 配乐 ducking | `sidechaincompress`（人声触发 BGM 压低）+ `amix` | 参数标定见 §5.2。**必须用真实素材标定** |
| 封面 | 抽"画面信息量最高"的帧 + **libass 渲标题** → 1280×720 jpg | ⚠️ 不是 `drawtext`（R26，构建级段错误）。字体随包分发（思源黑体 Bold，OFL 许可） |
| **转录** | `-af "whisper=model={ggml}:language=zh:format=json:destination=out.json:use_gpu=false"` | 需配 `-f null -` 作输出端；无 GPU 环境显式关 `use_gpu` |

### 5.2 成片增强（enhance.py，v1.13 新增）

阶段 4-A 实现。**全部与切片压在同一次编码里** —— 不做"先切后增强"两步走，
那会让画面多编码一代。

> ⚠️ **技术约束**：`-vf` 与 `-filter_complex` **不能同时使用**。
> 有 BGM 时必须把视频滤镜也搬进 `filter_complex`，否则报
> `Filtergraph 'subtitles=...' was specified through the -vf option ...`。

#### 5.2.1 转场：为什么不是 `xfade`

TASKS 原写"片段间 xfade 0.5s"，但**乙方案下每条候选是独立 mp4，
文件之间不存在相邻关系**，`xfade` 无从施展（它作用于同一滤镜图里的两路输入）。

另外实测：`xfade` 要求两路输入的**分辨率/像素格式/帧率完全一致**，
不一致时直接 `Conversion failed!` —— 错误信息完全不提"尺寸不匹配"。

⇒ 淡入淡出改为**单条片段自己的首尾 fade**：

```
fade=t=in:st=0:d={fade_in},fade=t=out:st={dur-fade_out}:d={fade_out}
```

**顺序上必须"先烧字幕、再 fade"** —— 反过来会让片尾画面黑了字幕还亮着。

#### 5.2.2 配乐 ducking：参数怎么标定（**最重要的一节**）

``` 
[bgm][voice]sidechaincompress=threshold=..:ratio=..:attack=..:release=..:makeup=1[ducked]
[voice][ducked]amix=inputs=2:duration=first:normalize=0
```

> ⚠️ **`[bgm]` 被 `sidechaincompress` 消费后不能再作输出。**
> 想同时拿到"原始 BGM"与"压缩后 BGM"（做对比测量）必须 `asplit` 分流，
> 否则报 `Output with label 'bgm' does not exist in any defined filter graph`。

**参数不是猜的，是用真实素材做受控实验标出来的**：

素材构造（不要用 `silencedetect` 去猜哪段没人说话 ——
直播素材常常全程有声，各阈值都抓不到静音）：

```
第 1 段（0~T）   真实直播人声        ← 应该压
第 2 段（T~2T）  纯静音（anullsrc）   ← 应该恢复
```

再把 BGM 轨**单独输出**（不含人声）来测 —— 电平差就是纯粹的压缩量。

标定结果（真实人声 RMS -14.2dB / 峰值 -0.56dB ⇒ 峰值线性 ≈ 0.94）：

| threshold | ratio | 人声段压低 | **静音段压低** | 说明 |
|---|---|---|---|---|
| 0.05 | 8 | 15.40 dB | 0.00 dB | 过强 |
| 0.10 | 8 | 10.20 dB | 0.00 dB | 强 |
| **0.20** | **8** | **5.00 dB** | **0.00 dB** | **默认** |
| 0.30 | 8 | 2.30 dB | 0.00 dB | 轻 |
| 0.50 | 8 | 0.60 dB | 0.00 dB | 太弱 |
| 0.20 | 4 | 4.30 dB | 0.00 dB | 轻 |

> ★ **验收指标是「静音段压低」这一列，不是「人声段压低」。**
> 它恒为 0.00dB ⇒ 压缩器在没人声时**完全恢复**，确实在跟随人声。
> 参数过敏（一直压着不放）同样能让"人声段压低"很好看，
> 所以**只测前者是不够的**。

**「让位强度」四档**（界面术语，不暴露 threshold/ratio）：
不压低 / 轻柔(0.3,4) / 标准(0.2,8) / 强力(0.1,8)。

#### 5.2.3 ★ 硬约束：测试信号的电平必须与真实素材对齐

```
ffmpeg 的 sine 滤镜默认振幅是 0.125（-18dBFS），不是满刻度！
    裸 sine        峰值 -18.06dB   线性 0.125
    真实直播人声    峰值  -0.74dB   线性 0.92    ← 差 7.4 倍（18dB）
```

用 `sine` 当"人声"标定压缩器阈值，会得到一个**低 18dB 的假阈值**，
搬到真实素材上直接把 BGM 压死（实测：压 23.8dB 且全程咬着不放）。

**要指定幅度就用 `aevalsrc`**：

```
-f lavfi -i "aevalsrc=exprs=0.9*sin(2*PI*440*t):s=48000:d=1.5"
```

这条约束适用于**所有音频参数标定**，不只 ducking。

#### 5.2.4 BGM 的来源

**刻意不内置音乐。** 音频版权不能像字体那样"附一份 LICENSE 就随包分发"——
免版税（royalty-free）≠ 免署名，更不等于可再分发。把来源不明的音频打进安装包，
风险直接转嫁给使用者。

做法：`%APPDATA%/SliceQ/bgm/` + 目录内《使用说明》（列出几个可合法取得素材的来源），
用户自备。`resolve_bgm()` 支持文件名 / 绝对路径 / 省略扩展名。

#### 5.2.5 封面

```
抽帧选帧 → 生成封面专用 ASS（一条大标题） → libass 渲染 → 1280×720 jpg
```

- **抽帧选帧**：均匀采样 8 帧（避开首尾 8%）→ 用 PIL 算"边缘方差 × 亮度惩罚"
  挑信息量最高的一帧。**不引入 numpy**（少一个依赖）。
  > PRD 说"最高评分帧"，但候选的 `score` 是**整段**评分、不是逐帧的。
  > 逐帧评分模型不在 v1 范围，这里用"画面信息量最高"作代理指标 ——
  > 比"随机取第一帧"强得多，且不需要额外模型调用。
- **字号自适应**：从设定字号往下试，直到行数 ≤ 3。
  中文没有空格，libass 不会自动换行（会直接溢出裁切），必须自己分行。
- **字体校验**：libass 遇到缺失字体**静默 fallback**（不报错不警告）。
  所以 `pick_cover_font()` 会校验可用性，替换时在结果里写明。

### 5.1 FFmpeg 分发与许可（v1.2 精确化）

**实测本机构建配置**：`--enable-gpl --enable-version3 --enable-libx264 --enable-libass`
→ **gyan.dev 的构建是 GPL 授权，不是 LGPL。**

**合规红线（必须写进开发者须知并做代码审查专项）：**

| 做法 | 合规性 |
|---|---|
| subprocess 调用独立的 `ffmpeg.exe` | ✅ **合法聚合（aggregate）**，SliceQ 可保持 MIT |
| PyInstaller 把 `ffmpeg.exe` 打进单文件 exe | ❌ **构成单一作品传播，SliceQ 须整体改为 GPL** —— 硬红线 |

**分发方式**：不打包进 exe。首次启动检测 `PATH` 与 `%APPDATA%/SliceQ/bin/ffmpeg.exe`；缺失则引导自动下载 gyan.dev **full build**（含 whisper 滤镜；essentials 不带）。

**模型文件**：ggml whisper 模型不在 ffmpeg 包内，需另行引导下载（走 hf-mirror.com 镜像，实测可通）。三档：tiny 77MB / base 142MB / small 466MB（中文推荐 small）。

**若用户自备的 ffmpeg 不带 `--enable-whisper`**：asr.py 需自动探测并降级到 faster-whisper。

## 5.7 任务状态落库（v1.18 下沉到 pipeline）

### 缺陷本身

`store.set_task_status` 原先**全写在 `clips_page` 的 UI 回调里**：

    _on_progress → 阶段状态（转录中 / 粗筛中 / 精析中）
    _on_done     → 待精析 / 待导出
    _on_error    → 出错

单任务路径工作正常。但分析队列走的是 `run_analysis`（模块级函数，
直接调 `pipeline.run`），**不经过这些回调** ⇒ 队列跑完，
任务状态**永远停在「已导入」**，而且**不报任何错**。

### 修法：状态由执行者维护

    状态是**任务的属性** —— 该由**执行者**维护，不该由**显示者**维护。

全部下沉到 `pipeline.run()`：

| 位置 | 写入 |
|---|---|
| `report()`（阶段变化时，`_STAGE_STATUS`）| 转录中 / 粗筛中 / 精析中 |
| 两个返回点 | `ready`（跑完）/ `screened`（停在确认点）|
| `run()` 包装层 · 异常 | `error` |
| `run()` 包装层 · `Cancelled` | `cancelled`（**不是 error**）|

`clips_page` 里那几处**全部删掉** —— 两处都写会互相覆盖。

### 三个细节

**① 取消 ≠ 出错。** 原来是 `error`，用户按了取消却看到"出错"，
会以为程序坏了。新增 `STATUS_CANCELLED`（「已取消」）。

**② 包装层而不是改函数体。** `run()` 只做 try/except + 转发，
主体留在 `_run_pipeline()`。这样异常路径的状态落库只有一处，
不会漏。`_run_pipeline` 的 docstring 里写了"不要直接调用"。

**③ 落库失败不能让分析挂掉。** `_mark()` 吞掉异常 ——
状态只是记账，记不上不该拖垮整条流水线
（与 `save_transcript_segs` 同样的取舍）。
自测里专门有一条验证这个。

验证：`selftest_pipeline_status.py`（16 项）覆盖四条路径。
端到端里也验了（修复前那三条 FAIL 就是它报出来的）。

## 5.5 多录像队列（ui/queue.py，v1.17 新增）

任务页支持 **Ctrl / Shift 多选**，一次把几条录像排队，一条接一条自动分析。
对应验收标准「两条录像批量入队，顺序完成，无限流报错」。

### ★ 队列是串行的 —— 这是实测结论，不是保守

| 场景 | 墙钟 | 加速 | 显存峰值 |
|---|---|---|---|
| 串行 1 路 | 82.66s | 1.00× | 5209 MB |
| 并发 2 路 | 73.75s | 1.12× | 7106 MB |
| 并发 4 路 | 144.16s | **0.57×（倒挂）** | 7541 MB |

单片耗时最说明问题：并发 4 路时片 0 从 23s 变成 **144s** —— 四个 whisper
进程抢同一块 GPU，总计算量没变，只是多了上下文切换与显存换页。
两种并发的**结果完全一致**（md5 相同）⇒ 并发不改结果，只是白花时间和显存。

所以「多条录像同时跑」是**负收益**。想更快应该调高**单条任务内部**的
粗筛/精析并发（那是网络 IO 密集，不一样）。

### 为什么不持久化

队列只在本次运行有效，关程序就清空。三个理由：

1. **重启后的语义说不清**。持久化就必须回答"上次退出时正在跑的那条算
   什么状态"，而真相是"跑到一半" —— 既非完成也非未开始。
2. **代价很低**。pipeline 自己有断点续跑（转录分片缓存 + 粗筛窗口缓存），
   重开程序再点一次「分析」，跑过的部分不重复花钱。
3. **不持久化反而更好懂**。下次打开看到"有 2 个任务在排队"却没在跑，
   比看不到队列更困惑。

⇒ 界面上**必须写明这一点**（队列面板底部有一行常驻说明）。

### 三条实现约束

| 约束 | 原因 |
|---|---|
| **单条失败不中断整队** | 与 `export_clips` 同样取舍。三条排着，第一条文件损坏不该让后两条也不跑 |
| **用户取消 = 整队停** | 那是"我不想跑了"，与"这条本身出错"是两回事。剩余项标 `skipped` |
| **路径在执行时现取** | 不在入队时快照 `source_path` —— 否则会出现"入队时有效、跑到时文件已被移走" |

### 界面上的两个细节

**① 状态列同步不能重建表格。** 队列跑的时候用户很可能正在挑下一批
（多选状态是有价值的）。`refresh()` 会 `setRowCount(0)` 重建，
把选择和滚动位置全冲掉。所以另写 `_sync_table_status()`：
按 task_id 找到行、只改第 3 列文本，并按 1.2s 节流。

**② 关程序时要拦一下。** 队列在跑时关窗口会中断一条流水线；
不拦的话进程被强杀，库里会留下"状态是 refining 但实际没在跑"的任务。
`closeEvent` 里弹确认，用户选「否」则 `event.ignore()`。

## 5.6 为什么转录不做并发（v1.17 实测否决）

F15 原文写「转录/粗筛/精析并发度可配置」。粗筛与精析做了（§5.3），
**转录经实测后决定不做**。方法：从真实录播切 N 片等长音频，
走产品代码 `asr.transcribe_chunk()`，对比串行 / 并发 2 / 并发 4。

### 数据（RTX 4060 Laptop 8GB，已占用 3.3GB；large-v3-turbo）

| 场景 | 墙钟 | 加速 | 显存峰值 | 单片耗时 |
|---|---|---|---|---|
| 串行 1 路 | 82.66s | 1.00× | 5209 MB | 23.3 / 21.7 / 21.3 / 16.5 |
| 并发 2 路 | 73.75s | 1.12× | 7106 MB | 66.5 / 24.1 / 28.5 / 21.2 |
| 并发 4 路 | 144.16s | **0.57×** | 7541 MB | 全都在 92~144s |

**结果一致性**：三个场景的文本 md5 完全相同（`7c4790512a49`），
段落数也完全一致（68/66/72/76）。⇒ 并发**不改结果**，纯属白花代价。

### 三条认识

1. **GPU 的计算单元是共享的**，whisper 本身就是 GPU 密集。
   多进程只是把同样的计算摊开，还得付出上下文切换与显存换页。
2. **显存是硬约束**。2 路就把峰值推到 7.1G —— 在 8G 卡上，用户同时开着
   游戏/浏览器就 OOM 了。为 12% 的收益冒这个险不值得。
3. **验证设计要对齐**：并发度提高后单片耗时反而变长（23s → 144s），
   说明瓶颈从"单片算力"变成了"GPU 争用"。

### CPU 路径：**未完成实测**（本阶段的缺口，如实记录）

尝试过（`--cpu --seg=25 --n=2 --maxw=2`），但连续两轮都跑不完 ——
第一次 20 分钟仍在第一个场景，第二次 11 分钟连一片都没出结果。
CPU 上的 whisper 慢到让这个实验的成本远超它的决策价值。

**决策不依赖它**：即便 CPU 模式下并发确实能快，也不该为此实现 ——

- CPU 模式本身就是慢路径（阶段 2 实测比 GPU 慢 6~9 倍），不是推荐配置；
- 实现要改 `asr` 的分片调度、并按 GPU/CPU 分支给不同并发度，
  复杂度和出错面都在增加，而收益只落在少数没 N 卡的机器上；
- 这是「不为慢路径增加复杂度」的取舍。

> ⚠️ **必须区分开**：GPU 那一节是**实测**，这一节是**推理**。
> 不要因为两者结论相同就把它们写成同一件事 —— 推理可以被推翻，
> 实测不行。要验证的话，脚本留了 `--cpu` 开关
> （`probe_asr_concurrency.py --cpu --seg=25 --n=2 --maxw=2`）。

> **对未做项要写明"为什么不做"**。只写"未做"，下一个接手的人会以为
> 是漏掉了，然后重新实现一个被数据否决过的东西。

### 6.1 剪映通道（v1.2 双向修正）

**修正一：砍掉"程序化触发剪映导出"的预期。**
剪映 7+ 已隐藏导出相关 UI 控件，`JianyingController.export_draft()`（依赖 `uiautomation`）仅在剪映 6 及以下可用。**SliceQ 只负责生成草稿，成片渲染由用户在剪映界面手动完成。** 这一点必须写进 UI 文案，避免用户期待"一键出片到剪映"。

**修正二：剪映升为草稿导出的首选通道。**
FCP XML 无原生字幕轨（§6.2），而剪映通道能携带**可编辑的字幕轨与标题轨**。字幕是切片视频的刚需，故字幕体验完整的剪映通道应为主推。

**关键实现认知（阶段 0 实测）：**

1. 剪映 6.0+ 对 `draft_content.json` / `draft_meta_info.json` **双文件加密**（实测 10.9、11.5.3 均如此）。
2. **但我们走的是「从零生成新草稿」，不是「读/改已有草稿」——恰好落在加密影响范围之外。** 生成的明文 JSON 由剪映首次读取时自行迁移并加密。
3. 剪映**不扫目录**，读根目录 `root_meta_info.json`（明文）的 `all_draft_store` 索引；剪映会在扫描时自行登记外部放入的草稿。
4. 生成的草稿结构比剪映原生草稿精简（2 个 JSON vs 15~20 项），**已实测可被接纳**，代价是列表缩略图缺失（无 `draft_cover.jpg`）。

**⚠️ 新增风险 R11（版本漂移）**：剪映会**静默强制全量升级**（实测：`bSilentInstall=1, bForceInstall=1`，包体 ~860MB，`Apps/` 目录从 10.9.0.14199 整体替换为 11.5.3.14501，不询问用户）。pyJianYingDraft 官方支持矩阵只标到剪映 10.8。**用户端版本不可控，已验证的格式随时可能失效。**

缓解措施（本 MVP 范围）：
- 启动时读取 `%LOCALAPPDATA%\JianyingPro\Apps\` 下的版本目录名，与已验证版本列表比对；未验证版本在导出前显示"剪映格式兼容性未验证"提示
- **保留降级通道**：剪映导出失败时，自动退回「片段 mp4 + SRT + 图文导入说明」打包
- 阶段 5 验收时把"生成草稿 → 剪映登记成功"做成可复现的检查项

#### 6.2.1 脚本直连：已弃用（阶段 0.5-B 实测）

曾评估用 DaVinci Resolve 官方 Python 脚本 API **直接驱动**达芬奇（免去人工导入）。**实测结论：不可行。**

| 检查项 | 结果 | 排除的假设 |
|---|---|---|
| `fusionscript.dll` PE 导入表 | 无任何 `python*.dll` 依赖 | ~~Python ABI 版本不匹配~~ |
| 依赖 DLL（`lua5.1`/`tbbmalloc`/VC 运行时） | 全部存在于安装目录（234 个 DLL） | ~~依赖缺失~~ |
| `os.add_dll_directory()` 干预 | 无效，仍崩溃 | ~~DLL 搜索路径问题~~ |
| `faulthandler` 捕获 | `0xC0000005` 访问冲突，崩于 `create_module` | 崩点在原生 `DllMain` |
| 导出表 | 含 `Py3ScriptLanguage`/`Py3ScriptState` 等类 | DLL 内嵌脚本引擎，反向驱动 Python |

**根因**：`fusionscript.dll` 在被 `LoadLibraryEx` 映射的瞬间（`DllMain` 内）执行非法内存访问，触发原生访问冲突。**该崩溃不可被 Python 捕获**（连 `faulthandler` 都拿不到 Python 栈）。

**弃用理由（技术可行性 ≠ 产品可行性）**：即使在本机修复，该 DLL 的加载对**安装路径、达芬奇版本（Studio/免费、19.x/21.x）、Python 环境、VC++ 运行时、管理员权限**极度敏感。而 SliceQ 是 BYOK + 单 exe 分发给多个切片 man 的产品——直连作为内置能力会把**每一类用户环境差异转化为一次进程段错误**，且**无任何可读错误信息**（进程直接消失）。这是不可接受的体验与不可维护的支持成本。

**完整证据链**：`stage0/reports/STAGE0.5B-RESOLVE-SCRIPTING-VERIFICATION.md`

#### 6.2.3 格式选择结论：**放弃 FCP7 XML，直出 OTIO**

**根因分析**：阶段 0 选择 `otio-fcp-adapter` → FCP7 XML 的路线，基于一个**从未被验证的假设**——"PR 和达芬奇都用 FCP7 XML"。实测证伪：

1. **达芬奇原生支持 OTIO**（官方 README 明确列出支持格式：`AAF/EDL/XML/FCPXML/DRT/ADL/OTIO`），不需要经过 FCP7 这层老格式翻译。
2. **FCP7 XML 是 2011 年停更的格式**（对应 Final Cut Pro 7），达芬奇对它是"兼容性导入"，容错与识别路径都更差。
3. **翻译过程本身引入缺陷**——适配器产出重复 `<rate>` 块与空 `<format/>`，我们还要额外写 `patch_fcp7_xml.py` 去修补。**绕过翻译层，这些缺陷根本不存在。**

> **教训**：不要为了迁就第三方适配器的输出格式，而绕开目标软件的原生通道。**先查目标软件支持什么，再决定输出什么**，而不是先选工具再假设目标兼容。

**新的导出策略**：

| 目标软件 | 导出格式 | 状态 |
|---|---|---|
| **达芬奇** | **OTIO（`.otio`）** | ✅ 实测通过 |
| 剪映 | 剪映草稿（`pyJianYingDraft`） | ✅ 阶段 0 已通过 |
| PR（Premiere） | 待定 —— 需实测 PR 是否支持 OTIO 导入 | ⏳ 未验证 |
| 通用兜底 | 片段 mp4 + SRT + 图文说明 | 设计已定 |

**FCP7 XML 通道保留为兼容选项**（部分老工具只认它），但**不再是达芬奇的首选路径**，且导出时必须经过 `patch_fcp7_xml.py` 修补。

**OTIO 导出的实现要点（与 XML 路线的差异）**：

1. **不需要 `otio-fcp-adapter`** —— 直接用 `opentimelineio` 主包内置的 `otio_json` 适配器：`otio.adapters.write_to_file(timeline, "out.otio")`。
2. **仍然必须设 `available_range`** —— 这是 OTIO 数据模型的完整性要求，与用哪个适配器无关。
3. **`target_url` 必须是绝对路径** —— 实测写法 `file:///C:/Users/.../source.mp4`（三斜杠 + 正斜杠）被达芬奇接受。
4. **Marker 建议用 OTIO 原生 `Marker` 对象** —— 而非"标记+附 SRT"的变通方案。待验证达芬奇是否保留（见 §6.2.4）。

#### 6.2.4.1 ⚠️ 架构级硬约束：OTIO 没有"字幕轨"概念

**实测确认（OTIO 0.18.1）**：`TrackKind` **只有两个值**。

```python
>>> otio.schema.TrackKind.Audio   # 'Audio'
>>> otio.schema.TrackKind.Video   # 'Video'
>>> otio.schema.TrackKind.Text    # AttributeError —— 不存在
```

**这意味着**：

1. **OTIO 标准中没有 `Text` / `Subtitle` 轨类型。** 字幕**不能**作为"文本轨"直接承载。
2. 可行路径只有三条，且都需实测验证：
   - **路径 ①：Marker 承载** —— 字幕/说明放 `Marker.name`。风险：条数多时语义混乱，且同样受 `Fallback` 影响。
   - **路径 ②：独立轨 + `Clip.name` 承载** —— 字幕文本放在片段名上。**不优雅但可能可用**（待验 C4）。
   - **路径 ③：烧录为透明视频层** —— 字幕渲染成带 alpha 的视频，放第二视频轨（待验 D4）。
3. **`Clip.name` 是唯一能承载任意文本的字段**。`Clip.metadata`（字典）虽可放结构化数据，但**外部软件不保证读取 metadata**。

**对字幕架构的影响**：字幕传递**不能依赖 OTIO 的轨道类型系统**，必须走三条变通路径之一。**阶段 4 正式立项设计。**

#### 6.2.5 保留的 XML 路线实现坑（仅当使用 FCP7 兼容通道时适用）

1. **FCP 适配器不在 `opentimelineio` pip 主包内。** 必须额外安装 **`otio-fcp-adapter`**（提供 `fcp_xml`，suffix `.xml`）。
2. **媒体引用必须设 `available_range`。** 缺失时适配器抛 `AttributeError: 'NoneType' object has no attribute 'start_time'`（`otio_fcp_adapter/fcp_xml.py:1482`）。
3. **FCP XML 无原生字幕轨。** 字幕只能以「时间线标记（Marker）+ 附 SRT 文件」携带。
4. **适配器输出必须后处理。** 产出 XML 含重复 `<rate>` 块与空 `<format/>`，必须调用 `patch_fcp7_xml.py` 修补。

### 6.3.2 字幕通道：SRT（已查证可行）

**结论：达芬奇免费版原生支持 SRT 导入，无需 Studio。**

| 项目 | 事实 |
|------|------|
| 导入路径 | `File > Import > Subtitle`，或媒体池右键 → `Import Subtitle` |
| 精确对位 | 右键字幕剪辑 → `Insert Selected Subtitles to Timeline Using Timecode` |

### 6.3.3 时间码起点陷阱（R20，**✅ 已定论：依赖帧率匹配，必须写进用户文档**）

**问题**：达芬奇新建时间线的默认起始时间码是 `01:00:00:00`，而 SRT 是零基的。

**三个来源独立确认了这是高频踩坑**（cutconvert.com / creativevideotips.com / 犹他大学 wiki）。

#### 🔴 修正（2026-09-27 真机验收）

**原结论（2026-09-25，样本 E）**：
> ✅ 实测定论：OTIO 中显式写 `global_start_time = 0` 后，
> 达芬奇时间线起始时间码 = `00:00:00:00`。
> **⇒ 达芬奇会读取并采用 OTIO 的 `global_start_time`。解法①成立，R20 已可控。**

**本次实测不支持该因果结论。** 证据（达芬奇项目库 `Sm2Sequence.MediaExtents`
解码为 `[起始偏移秒, 时间线总长秒]`）：

| 项目 | 项目帧率 | 起始偏移 | 总长 | OTIO 的 `global_start_time` | rate 匹配项目？ |
|---|---|---|---|---|---|
| 新建项目 1（9-26） | 24 | **3600.0**（1h） | 38.625 | （无 OTIO） | — |
| 新建项目 2（9-27 15:24） | 30 | **0.0** | 60.0 | `0.0/30.0` | ✅ 匹配 |
| 新建项目 3（9-27 21:12） | 24 | **3600.0**（1h） | 135.0 | `0.0/20.0` | ❌ 不匹配 |

**当时存在两种解释，事后已区分（见下）：**

- **H1（起始 TC 是项目属性）**：项目 1 **从未导入过 OTIO**，起始偏移一样是 3600
  ⇒ `01:00:00:00` 是新建项目的默认值；项目 2 的 0 来自**手动设置**。
- **H2（rate 匹配才生效）**：项目 2 `rate=30` 与项目 30fps **匹配** → 起点 0；
  项目 3 `rate=20` 与项目 24fps **不匹配** → 回退默认 3600。项目 1 不构成反例。

#### ✅ 定论（2026-09-27，用户回答后）

区分方法就是问一句"上次是否手动改过项目起始时间码"。
**用户确认：没有改过 ⇒ H1 被否证，H2 成立。**

> **达芬奇确实会读取并采用 OTIO 的 `global_start_time`
> —— 但前提是 OTIO 的 `rate` 与达芬奇项目帧率一致。**
> 不一致时，达芬奇**丢弃**该字段、回退到项目自己的起始时间码（新建项目默认 `01:00:00:00`）。

⇒ **原结论方向是对的，只是缺了这个前提条件**（样本 E 当时大概恰好 rate 匹配）。

#### 解法（已写进 `导入说明.txt`）

| # | 做法 | 说明 |
|---|------|------|
| **① 首选** | 新建项目时把**项目/时间线帧率设为素材帧率** | rate 匹配 ⇒ `global_start_time = 0` 生效 ⇒ 起点 `00:00:00:00`，字幕零摩擦对位 |
| **② 兜底** | 项目已建好时，去「项目设置 → 主设置 → 时间线起始时间码」改成 `00:00:00:00` | 覆盖帧率已无法更改的场景 |

❌ **不能靠改 OTIO 的 `rate` 去凑达芬奇的默认帧率。**
`rate` 必须写**素材真实帧率**，否则切点的帧↔秒换算会错
（实测：项目 24fps + OTIO 20fps 的 ×1.2 重采样精确到 <1 帧，前提就是 rate 写对了）。
把 rate 写成 24 会让 `source_range` 整体偏移，**时长和位置全错** —— 比时间码问题严重得多。

⚠️ **帧率不一致只影响起始时间码，不影响片段本身的位置和时长**
（达芬奇会自动换算）。这一点要在用户文档里说清，否则用户会以为文件坏了。

#### 影响面

| 场景 | 影响 |
|---|---|
| 片段在时间线上的相对位置 | ❌ 无影响（相对位置精确正确，0/45/90s，无缝） |
| `rate` 不匹配时片段时长 | ❌ 无影响（达芬奇按项目帧率自动换算，实测误差 <1 帧） |
| 用户**手动按时间码**输入/对字幕 | 🔴 有影响：整体偏移 1 小时（R20 原始场景） |
| 用户**导入 .srt**（按时间码插入） | ✅ **已验证**：基准正确 —— 达芬奇按其时间线起点对齐，零基 SRT 正好落在片段上 |
| 用户**把 .srt 拖到时间线** | 🔴 **实测整体提前约 0.54s**（丢首条偏移），见 §6.3.3.1 |

#### 缓解措施（v1.23 状态）

| # | 措施 | 现状 |
|---|------|------|
| ① | 导出 OTIO 时始终写入 `Timeline.global_start_time = 0` | 已实现；**在 rate 匹配时生效**（H2 定论）⇒ 仍要写，但不能当唯一手段 |
| ② | `导入说明.txt` 写明"项目帧率设为素材帧率"（首选） | ✅ **v1.23 已补**（原先声称有、实际没有） |
| ③ | `导入说明.txt` 写明"手动改时间线起始时间码 `00:00:00:00`"（兜底） | ✅ **v1.23 已补** |

❌ **仍不采用**"导出时给 SRT 时间码 +1h"——治标，换软件就错。

### 6.3.3.1 🔴 SRT 不能直接拖进达芬奇（2026-09-27 新发现）

**实测**：用户把并行导出的 `.srt` 拖进达芬奇后，**32 条字幕全部偏移 13 帧（0.54 秒）**，
偏差**恒定不变**：

| 时间线时间（达芬奇） | SRT 时间 | 差 |
|---|---|---|
| 0.000s | 0.543s | −0.543 |
| 5.083s | 5.608s | −0.525 |
| 8.917s | 9.448s | −0.531 |
| 13.375s | 13.903s | −0.528 |

**根因**：拖拽 / 顺序插入时，达芬奇**从时间线第 0 帧开始依次排列**，
因此**丢掉第一条字幕的起始偏移**（首条 SRT 起始 = 0.543s）。
后续条目按间隔排列保持正确，所以偏差恒定为"首条起始时间"。

⚠️ **注意这**不是** R20**：R20 的表现是"整体偏 1 小时"，而这里是**亚秒级偏移**。
这个差别说明达芬奇的**对齐基准是对的**（它确实按时间线起点对齐），
问题只在**插入方式**。

**⇒ 处理**：`导入说明.txt` 里明确写：
- ✅ 用 `File > Import > Subtitle...` + 字幕轨右键
  **Insert Selected Subtitles to Timeline Using Timecode**（按时间码插入）
- ❌ 不要直接把 `.srt` 拖到时间线上

⏳ **待复验**：改用"按时间码插入"后是否零偏移（材料已在同一批 SRT 上备好）。

### 6.3.4 数据模型预留（阶段 1 必做）

即使 v1 字幕只走 SRT，SQLite 也**必须现在建好**以下两表（用户已确认愿意为 v2 预留）：

```sql
-- 字幕轨（v1 用于生成 SRT；v2 用于三端可编辑时间线）
CREATE TABLE subtitle (
    cue_id      INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id     INTEGER NOT NULL,
    start_ms    INTEGER NOT NULL,   -- 相对切片起点，零基
    end_ms      INTEGER NOT NULL,
    text        TEXT    NOT NULL,
    style_hint  TEXT,               -- 预留给 v2 的样式描述（JSON）
    FOREIGN KEY (task_id) REFERENCES task(task_id)
);

-- 高光标记（用于 OTIO 的 Marker 通道）
CREATE TABLE marker (
    marker_id   INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id     INTEGER NOT NULL,
    at_ms       INTEGER NOT NULL,   -- 相对切片起点，零基
    name        TEXT    NOT NULL,   -- 高光说明（长度上限待样本 F 结论）
    color       TEXT    DEFAULT 'CYAN',
    FOREIGN KEY (task_id) REFERENCES task(task_id)
);
```

**为什么不等到 v2 再建**：v2 做三端适配时若发现表结构不对，要推翻重做时间线数据模型——
**现在的建表成本 ≈ 0，未来的迁移成本很高。**

### 6.3.5 字幕轨 vs Text+ 标题（两条不同路线，勿混淆）

| | 字幕轨（Subtitle Track） | Text+ 标题（Title） |
|---|---|---|
| 位置 | 视频轨上方专用轨 | 视频轨上的片段 |
| 导入 SRT | ✅ 原生 | ❌ |
| 导出 SRT | ✅ | ❌ **按钮直接灰掉** |
| 逐条独立样式 | ❌ 只能整轨统一 | ✅ |
| SliceQ v1 采用 | ✅ **是** | ❌ 否 |
| SliceQ v2 可选 | — | ⏳ 需 FCPXML 输出才能实现 |

**v2 增强项**：若用户需要"每条字幕独立调样式"，需新增 **FCPXML 标题导出通道**。
列为**未来可选增强**，不阻塞 v1。

## 6.4 甲方案落地设计：OTIO 引用原始源视频（v1.7 新增，2026-09-25 决策）

### 6.4.1 决策记录

用户于 2026-09-25 选择 **甲方案**：导出的 OTIO **引用原始源视频**，用 `source_range` 承载切点。

| 方案 | OTIO 引用对象 | 结果 |
|---|--------------|------|
| **甲** | **原始源视频 + `source_range`** | ✅ **选定** |
| 乙 | SliceQ 切出的成片 MP4 | 未选 |
| 丙 | 每个高光切成独立 MP4 | 未选 |

**选定理由**（用户确认"用户会在切片基础上继续调切点、换顺序"）：
语义最正确——用户可在达芬奇里任意调整切点、重排片段、延长缩短，这才是"精修"的实质。
乙方案时间线上只有 1 个片段，精修意义弱；丙方案交付形态变成"一堆小文件"。

### 6.4.2 数据结构

```
Timeline "SliceQ_<任务名>"
  global_start_time = 0                    ← 必须写（R20：仅在 rate 与项目帧率一致时生效）
  Stack "tracks"
    Track "SliceQ_主轨" (kind = Video)      ← ★★ 必须两条轨都有
      Clip "高光1_<标题>"   media_reference → 原始源视频（同一文件）
                            source_range = TimeRange(start=高光1入点, duration=高光1时长)
      Clip "高光2_<标题>"   ...
      ...
    Track "SliceQ_主音轨" (kind = Audio)    ← ★★ v1.23 新增
      Clip "高光1_<标题>"   media_reference → 同一个源视频
                            source_range = 与视频轨**逐段一致**
      ...
```

> 🔴 **v1.23 修正：原设计只有 Video Track，后果是达芬奇里"有画面、没声音"。**
> 达芬奇**不会**从视频片段自动推断出音频 —— 它会自己建一条音频轨，但**是空的**。
> 实测证据（2026-09-27 真机）：项目库 `Sm2TiTrack` 有 2 行（视频轨 + 音频轨），
> 但 `Sm2TiItem` 的 3 个片段**全部**挂在视频轨上，音频轨 0 个片段。

**要点**：
- 所有 Clip 引用**同一个**原始源视频文件（音视频两条轨都是）
- 切点信息全部存在 `Clip.source_range`（**不是**剪辑后的文件）
- 时间线总时长 = Σ 各高光时长，**不等于**源视频时长
- ⚠️ **两条轨要各建独立的 `Clip` 对象**：同一个 Clip 对象 append 到两条轨
  会互相覆盖 `range_in_parent`，表现为其中一条轨的片段位置错乱，**且不报错**。
  自测里有一条专门守这个（`音视频是不同的 Clip 对象`）。
- ⚠️ `Clip.range_in_parent = ...` 那句赋值**不会写进 `.otio` 文件**（位置由 Track
  按 `source_range` 时长累加算出）。它只是给实例赋属性、会 shadow 掉同名方法，
  属"看起来有用实际无输出影响"的代码 —— 保留但**不要依赖**。

**⚠️ 高光说明不再走 Marker（2026-09-25 实测定论）**

实测：样本 B 带 3 个青色 Marker，导入达芬奇后**时间线上没有任何标记**。
达芬奇走 `Import Log (Fallback)` 路径，**Marker 被丢弃**。

**⇒ 高光说明改放 `Clip.name`。** 理由：`Clip.name` 是唯一**既能承载任意文本、
又被外部软件稳定保留**的字段（实测：片段名 `切片1_开场高光` 在达芬奇里完整保留）。

**命名约定**：

```
Clip.name = "<序号>_<高光标题>"
```

- 序号帮助用户按顺序辨认
- 标题来自模型生成的高光描述（长度上限待样本 F 结论；暂定 20 字内）
- **不把长段落塞进 `Clip.name`**——它显示在时间线片段上，过长会被截断且难读

**完整的高光说明**（评分、类型、模型理由）写入随包的 `highlight.md` 或在应用内查看，
**不依赖 OTIO 承载**。

### 6.4.3 ⚠️ 关键连带后果：SRT 时间轴必须重映射（**甲方案最容易出错的一环**）

**问题**：SRT 的字幕时间戳原本对齐在**源视频的绝对时间轴**上；
而甲方案的时间线是**若干非连续片段的拼接**。两者时间轴不同。

**举例**：

| 片段 | 源视频时间 | 新时间线时间 |
|------|-----------|-------------|
| 高光 1 | 10s ~ 25s | 0s ~ 15s |
| 高光 2 | 100s ~ 115s | 15s ~ 30s |

源视频 **12s** 处的一句字幕 → 在新时间线里应落在 **2s** 处。

**重映射公式**：

```
给定源时间 source_t 落在第 i 个高光区间内：

timeline_t = source_t - highlight[i].start
             + Σ(highlight[0..i-1].duration)
```

**若漏做这一步的后果**：视频切好了、字幕也导进去了，
但**字幕整体错位**——而且因为 SRT 本身合法、达芬奇也正常接受，**不会有任何报错**。
用户看到的现象是"字幕全乱"，无从排查。**这是典型的"功能正常、结果全错"。**

**实现约束**：
- `subtitle.py` 输出 SRT 前**必须**过一遍重映射
- `editor.py` 烧录字幕时用的是新时间线时间轴
- **两处必须调用同一个映射函数**，禁止各写一份（否则烧录版与 SRT 版不一致）

**验收项（阶段 4 必须测）**：
抽 3 条字幕，人工核对"字幕文本 ↔ 画面对应关系"是否正确。**只看时间戳数字不够，必须看内容。**

### 6.4.4 媒体链接策略（**0.8-B 已实测定论**）

甲方案下，用户**必须保留原始源视频**才能打开时间线。

| 场景 | 预期行为 |
|------|---------|
| 同机、源片未移动、池中无同名文件 | **自动链接** ✅（实测通过） |
| 源片移动 / 改名 | 需手动重链接 |
| 换一台机器 | 必然需重链接 |
| **池中已有同名文件** | ⚠️ **可能链到那个同名文件（静默错配）**，见 R23 |

**✅ `target_url` 写法（0.8-B 实测定论）：五种写法全部可用。**

| 写法 | 结果 |
|------|------|
| `file:///C:/...` | ✅ |
| `file://localhost/C:/...` | ✅ |
| `C:/...`（纯路径·正斜杠） | ✅ |
| `C:\...`（纯路径·反斜杠） | ✅ |
| 相对路径 | ✅ |

⇒ **维持 `file:///C:/...`**（标准写法，且已验证）。

**⚠️ 但 `.otio` 首次导入仍有弹窗**：官方定义 `.otio` 不携带媒体，
当媒体不在池中时达芬奇会问「找不到片段」→ **`导入说明.txt` 必需**。

**⚠️ 同名冲突（R23，实测支持）**：达芬奇优先**按文件名**匹配池中已有条目；
池中无同名时才用 `target_url` 的路径。**⇒ `导入说明.txt` 需加入同名冲突提醒。**

**`.otioz` 不适用于甲方案**：它会把引用的媒体打包进去，
而甲方案引用的是**原始源视频**——直播录屏动辄几个 GB，打包不现实。**排除该选项。**

### 6.4.5 导出包构成（新增硬性要求）

甲方案下每次导出产出：

```
<任务名>/
  <任务名>.mp4          ← 成片（FFmpeg 剪出，可直接发布）
  <任务名>.srt          ← 字幕（已重映射到新时间线，零基，UTF-8 无 BOM）
  <任务名>.otio         ← 时间线（引用原始源视频 + 切点）
  导入说明.txt           ← ★ 必须生成，内容见下
```

**`导入说明.txt` 模板**（生成成本为零，但能挡掉一批"这软件没用"的评价）：

```
【SliceQ 导出包 · 导入说明】

本包含 3 个文件：
  1. <任务名>.mp4   —— 成片，可直接发布
  2. <任务名>.srt   —— 字幕文件
  3. <任务名>.otio  —— 可编辑时间线（需原始素材在本机）

────────────────────────────────
■ 只想直接发布
   用 <任务名>.mp4 即可。

────────────────────────────────
■ 想在达芬奇里继续精修切点
   1. File > Import > Timeline，选择 <任务名>.otio
   2. 若弹出「找不到片段」→ 点【是】，选择原始素材所在文件夹
      （说明：.otio 格式本身不携带媒体文件，这是正常现象，不是文件损坏）
   3. 源文件路径：<导出时自动填入源视频绝对路径>

────────────────────────────────
■ 想在达芬奇里加字幕
   1. 先把时间线起始时间码设为 00:00:00:00
      （在媒体池右键时间线 > 时间线 > 起始时间码）
   2. File > Import > Subtitle，选择 <任务名>.srt
   3. 把它拖到视频轨上方的灰色区域，会自动创建字幕轨

────────────────────────────────
■ 注意（重要）
   若你的媒体池中已经存在【同名】素材，达芬奇可能链接到那个同名文件，
   而不是本包指定的源文件。导入后请确认时间线指向的是正确的素材。
```

> ⚠️ 第 2 步的提示**必须写**。否则用户遇到弹窗会以为文件坏了——
> 这正是 2026-09-25 实测踩到的坑（见 `reports/STAGE0.8-OTIO-MEDIA-LINK-DIAGNOSIS.md`）。
> ⚠️「注意」段落对应 **R23**（同名静默错配，已实测支持）。

- **断点**：转录/粗筛/精析分段落库，程序崩溃后重开可从断段续跑。
- **异常**：无 ffmpeg / 无 whisper 模型 / 无 key / 下载失败 / API 余额不足 / 剪映未安装或版本未验证，均有明确中文错误提示与下一步指引。

## 10. 自测的数据隔离约定（v1.20 新增）

### 事故：跑一次自测，用户的 API key 就没了

2026-09-27 发现 `selftest_stage1.py` 直接操作生产路径：

| 代码 | 后果 |
|---|---|
| `secrets.set_api_key(fake)` | **覆盖用户的真 API key** |
| `secrets.clear_all()` | **删掉凭据文件** —— key 就此丢失 |
| `settings.set("whisper_model", "ggml-base.bin")` | 把 large-v3-turbo **降级成 base**，而用户**不会知道转录为什么变差** |

同类：

- `selftest_first_launch.py` —— 清掉用户手动指定的 ffmpeg 路径
- `selftest_bridge.py` —— **它自身没有一处 `settings.set`**，
  但调 `bridge.set_manual_path()`，而那个产品函数内部会写 `settings.json`

共同特征：**不报错**，而且**只在很久之后以别的形式暴露**
（那次是等到另一个依赖 key 的测试报 `AuthError` 才顺藤摸到）。

### 约定：默认隔离

所有自测 / 探针脚本开头必须写：

```python
from sliceq._testing import assert_isolated, isolate_data_root
isolate_data_root()
assert_isolated()
```

`isolate_data_root()` 把落盘位置重定向到临时目录（atexit 整个删除）：

| 路径 | 处理 | 理由 |
|---|---|---|
| `DB_PATH` / `SECRET_PATH` / `SETTINGS_PATH` | 隔离（凭据与设置**复制**一份副本）| 写一次就是真损失 |
| `STYLES_DIR` | 隔离 | 用户手改的字幕预设（阶段 3 的注入测试往这里留过垃圾预设，直接出现在用户下拉框里）|
| `EXPORT_DIR` / `LOGS_DIR` / `BGM_DIR` / `work/` | 隔离 | 测试产物不该混进用户目录 |
| `MODELS_DIR` / `BIN_DIR` | **❌ 故意不隔离** | 是**下载缓存**（1.8GB）。隔离会让测试被迫重新下载；而"补下载"对用户是**有益**的，不是破坏 |

**凭据与设置为什么要「复制」而不是「不复制」**：

- 不复制凭据 ⇒ 需要真实模型调用的 e2e 读不到 key，直接跑不起来；
- 不复制设置 ⇒ 测试读到的**不是用户真实在用的端点**。
  这一条当场付出过代价：隔离后测试用出厂默认端点（原生 API 通道），
  而用户配的是兼容模式 ⇒ 走了完全不同的通道 ⇒ e2e"0 条切片"。

> **判据**：写下去会不会**损坏**用户的既有数据。
> 模型 / ffmpeg 是"没有就补上"，样式 / 凭据 / 任务库是"改了就是损坏"。

`assert_isolated()` 把「忘了隔离」从**静默写用户数据**变成**测试当场失败**。

### 为什么是「重定向」而不是「测完恢复」

恢复要写对每一处、且中途不能崩；一旦异常就留下污染，
而污染是**静默**的（用户不会收到通知）。
重定向是从根上让「写生产数据」这件事**不可能发生**。

### 验收：不靠读代码，靠比指纹

`stage0/probe_resolve/check_isolation.py` 逐个跑测试，
跑前跑后比生产数据指纹（md5 + 大小 + **mtime** + 各表行数）。

**为什么不靠代码审查**：排查时我 grep 的是"测试文件里的 `settings.set`"，
因此**整轮都漏了 `selftest_bridge`** —— 它走的是间接调用。
最后是靠"跑一遍看文件 mtime 变没变"才逮到。

    md5 相同但 mtime 变了 → 文件被重写过（内容碰巧一样）。
    **这仍然算问题** —— 今天写的是同值，明天就可能是别的值。

### 附带收获：隔离会照出「隐式依赖外部状态」的测试

`selftest_stage2.py` **从来没有调用过 `store.init_db()`** ——
它一直是靠"生产库里已经有表"才跑得起来。
隔离到空库后立刻报 `no such table: task`。

这类测试意味着更糟的一件事：**在全新的环境里跑它必然失败**。
隔离把这类隐式依赖一次照了出来。

## 6.6 exporter.py 实现与验收（v1.21 新增）

### 三条通道

| 通道 | 产出 | 落点 |
|---|---|---|
| **剪映草稿** | 视频轨（引用源片 + 源内裁剪）+ 字幕轨 + 标题轨 | `%LOCALAPPDATA%/.../com.lveditor.draft/<名字>/` |
| **达芬奇** | `<名字>.otio`（甲方案）+ 并行 `.srt` + `导入说明.txt` | 输出目录下 `达芬奇/` |
| **降级包** | 每条候选一个 mp4 + SRT | 输出目录下 `降级包/`（**剪映失败时自动退回**）|

### ★ 唯一命名：为什么不用 `allow_replace=True`

前置实测 §5.3 记的就是这个遗留问题：

    `create_draft(allow_replace=True)` 会**静默覆盖**同名草稿 ——
    用户如果在剪映里精修过上一版，那一版会**凭空消失**，且没有任何提示。

实现改为 `_unique_name()`：探测重名后自动避让
（`草稿` → `草稿 (2)` → `草稿 (3)`），并配 `allow_replace=False`。

自测里专门锁了这条行为：导出两次 → 往**第一份**草稿里塞一个
"用户精修痕迹"文件 → 验证第二份**换了名字**、且第一份的
`draft_content.json` **一字节未改**。

### 字幕：**单一映射调用点**

`exporter.build_timeline_subtitles()` 是**唯一**把源时间轴字幕搬到时间线的地方：

    断句（subtitle.split_segments）
      → ★ 跨段重映射（subtitle.remap_to_timeline）
      → 写 SRT

剪映字幕轨、达芬奇并行 SRT、降级包 SRT **全都用它**。
不要在任何一条通道里另写一份映射 —— 那正是"传错不报错、字幕整体错位"的来源。

### 验收（2026-09-27）

| 项 | 结果 |
|---|---|
| `selftest_exporter.py` | **70/70**（`--slow` 含真切片时为 **73/73**）|
| 真实规模：2.5h 录播 / 5 段 / 1882 条字幕 | 全过 |
| 真实规模：12 段 / 540s | 全过 |

真实规模（12 段）的关键数字：

    时间线总长      540.000s（Σ片段时长 = 540.0s，**偏差 0.000s**）
    available_range 8958.9s == 素材真实总时长（不是片段时长）
    逐段 source_range 无累计漂移
    字幕            125 条，全部落在 0~540s，**12 段每段都有**
