# 异常注入测试报告 —— 「程序会不会死得很难看」

> 日期：2026-09-26｜关联：阶段 3 · `STAGE3-EDITOR-AND-SUBTITLE-RESULT.md`
> 脚本：`stage0/probe_resolve/selftest_fault_injection.py`（26 场景）
> ＋`stage0/probe_resolve/selftest_fault_quality.py`（35 项结果验证）

---

## 一、为什么要做这件事

阶段 3 的 70 项自测**覆盖的全是正常流程**。而那一轮抓到的三个缺陷
（`SystemExit` 穿透 / worker 引用丢失 / cwd 改变路径基准）**没有一个是正常流程
测出来的** —— 都是被环境撞出来的。

> 正常流程全过 ≠ 异常时不会死。

所以这一轮**故意制造故障**，看程序怎么反应。

---

## 二、合格标准

不是"有没有报错"，而是**用户能不能看懂、程序能不能继续**：

| 表现 | 判定 |
|---|---|
| 抛自定义错误 + 中文说明 + 说清怎么办 | ✅ 合格 |
| 明确降级并说明（例：容错回退） | ✅ 合格 |
| **返回"成功"但产物不存在/为空，且无任何说明** | ⚠️ 静默 |
| **裸 Python 异常**（`FileNotFoundError` 之类）→ 用户看不懂 | ⚠️ 误导 |
| **段错误 / 未捕获异常穿透** | 🔴 崩溃 |
| **永远等待** | 🔴 卡死 |

## 四、修复的两个真问题

### 4.1 错误信息没有区分"数据坏"和"时间不对"

**改前**：缺字段的条目报 `片段时间无效：0.0 → 0.0`

用户看到这句会懵 —— 他勾的片段明明有时间，为什么说"无效"？
而且**不知道该干什么**（改时间？重新分析？）

**改后**：两条路径分开说

```
缺字段  → 这一条缺少起止时间（数据不完整）。
          多半来自旧版本留下的记录 —— 重新分析一次即可。

时间倒挂 → 结束时间不晚于开始时间（30.0s → 10.0s），无法切片。
          请到「候选清单」页把这一条的起止时间改对。
```

**理由**：这两种情况的处理动作完全不同（重新分析 vs 改时间），
混在一句话里等于没给指引。

### 4.2 手动指定的 ffmpeg 路径无效时**静默回退**

`find_ffmpeg()` 的顺序是「应用目录 → 手动指定 → 系统 PATH」，
手动路径不存在时会**继续往后找** —— 这个回退本身是**对的**
（用户填错一个字符不该让程序不可用）。

**问题在于不说出来**：用户特意换成了带 whisper 的那份 ffmpeg，
路径打错一个字符，程序默默用了另一个（可能不带 whisper）。
他会一直以为"我设置过了"，然后在转录时撞上莫名其妙的失败。

**改法**：新增 `ffmpeg_tools.ffmpeg_source()`，返回来源与
`manual_invalid` 标志；`probe_environment()` 会把这件事说出来：

```
⚠️ 你在设置里指定的路径不存在：C:\...\xxx.exe，
   已自动改用「系统 PATH」。
```

## 五、我自己在这轮里犯的三个错（**比代码缺陷更值得记**）

### 5.1 判据太弱：只验证"没崩"，没验证"结果对"

第一轮 26 个场景里有 15 个的判定是"没抛异常 → 合格"。

**但一个函数完全可以"不抛异常地返回一堆错结果"。**
比如 B3（分段倒挂）—— 第一轮只告诉我"没崩"，至于生成的字幕是空的、
错的、还是正常的，**它一个字都没说**。

⇒ 补了第二轮，逐个检查产物。

### 5.2 手写期望值算错了（三处）

```
标签写"跨起点 80%"  → 实际相交比 37.5%
标签写"正好 55%"    → 实际 45.0%
```

我手算的相交比全是错的。**如果断言的是"应该保留/丢弃"，就会误报失败 ——
而失败的是我的算术，不是代码。**

这跟之前"肉眼估幻觉率"是同一个坑：
**判据必须是算出来的，不是估的。**

⇒ 改成用程序计算期望值。

### 5.3 把"正确的容错"当成了 bug

C1 场景我一开始判定为"静默失败"，因为"设了无效路径却导出成功"。

**但回退到可用 ffmpeg 才是正确行为。** 我的期望错了。

这一条差点让我去"修"一个没坏的地方 —— 而真正的缺陷（回退了不告知）
藏在旁边。

## 六、结论

**这轮没有抓到"崩溃"或"卡死"级别的缺陷** —— 上一轮修的那两个
（`Worker` 的 `BaseException` 捕获、worker 引用持有）确实是当时的
唯一重灾区，修完之后异常路径是稳的。

抓到的是**两类"不够好"**：
1. 错误信息不够准确（指向错的原因、不给下一步动作）
2. 容错了但不告知（用户以为设置生效了）

这两类不会让程序死，但会让用户**卡在"不知道为什么不行"**上 ——
从产品角度看，和崩溃一样致命。

## 七、还没覆盖的（诚实清单）

| # | 场景 | 为什么没测 |
|---|---|---|
| 1 | **磁盘写满** | 无法安全模拟（要真的占满磁盘） |
| 2 | **真实只读目录**（ACL 级） | 当前用「路径指向文件」近似模拟，不是真权限拒绝 |
| 3 | **导出中途强杀进程** | 会留下孤儿 ffmpeg，测试环境不便清理 |
| 4 | **并发导出**（两个任务同时导） | 未测；`_work` 目录按任务隔离，理论上不冲突 |
| 5 | **超长素材**（3 小时）的异常路径 | 耗时 |
| 6 | **GUI 层的异常呈现** | 离屏模式看不到弹窗/红色文字 |

> 第 6 条最实际：**错误信息的"最后一公里"是界面**。
> 现在验证的是"异常对象里有中文",没验证"用户真的看到了它"。
