## 3. F16 前置论证：**原计划的检测方式不可行**

TASKS 要求"开工前先重新论证检测方式"。实测结论比预想的更糟：

| 检测手段 | 实测结果 |
|---|---|
| `where videocaptioner` | ❌ PATH 无 |
| `pip show videocaptioner` | ❌ 未安装 |
| **注册表查询** | ❌ **`reg.exe` 被安全策略阻止**（沙箱程序黑名单）|
| **解析桌面快捷方式（COM）** | ❌ **COM 对象实例化被安全策略阻止** |
| 文件系统扫描（`%LOCALAPPDATA%`、`%APPDATA%`、Program Files） | ❌ 没找到任何 `VideoCaptioner.exe` |
| 数据目录 | ✅ 存在 `%APPDATA%\VideoCaptioner` |
| 桌面快捷方式 | ✅ 存在 `VideoCaptioner.lnk`（但目标解析不出来）|

**三项关键认识**：

1. **注册表探测不能作为唯一手段** —— 在受限环境里 `reg.exe` 会被直接拦掉。
   这不是本机特例：企业/受管机器上类似限制很常见。
2. **"数据目录存在"不等于"程序已安装"** —— 本机就是反例：
   数据目录和桌面快捷方式都在，但可执行文件找不到（可能已卸载留残留，或装在别处）。
3. **全盘扫描不现实** —— 用户可以把程序装在任意路径，扫全盘代价不可接受。

⇒ **F16 的正确形态应该是**（待实现）：

```
① 手动指定路径优先（像 ffmpeg 那样，用户在设置里填 VideoCaptioner.exe）
② 自动发现只作尽力而为的辅助（扫几个常见目录，失败不报错）
③ 找不到就降级为"引导用户手动打开 + 打开它的工作目录"
④ 不假设它有 CLI —— 官方是 Windows 安装包发行，是否有命令行子命令未验证
⑤ 独立进程调用，不 import、不打包（GPL 合规）
```

**本机无法真机验证**（程序没装），所以 F16 留到用户确认安装状态后再做。

## 4. F15 批量并发

### 4.1 新模块 `concurrency.py`

粗筛（按窗口）和精析（按候选）都需要同一套并发语义。**两处各写一遍必然漂移**，
而并发代码的漂移属于"偶发、难复现"那一类 —— 正是最不该有两份实现的地方。

三条设计约束：

| # | 约束 | 为什么 |
|---|---|---|
| ① | **回调在调用线程执行** | 成本累计/进度/落库都靠回调。若在工作线程里做，每个共享状态都要加锁，而"某个累加忘了加锁"表现为**钱偶尔少算一点**，几乎不可能复现 |
| ② | `workers <= 1` 走独立串行路径 | 保证默认配置下与并发前**行为一致**，且可被直接对照验证 |
| ③ | 取消 = 不再提交新任务 | Python 无法硬中断线程；假装能只会制造半途状态（发半截请求、落一半库）|

### 4.2 ★ 一个必须先想清楚的设计：窗口化提交

最初写的是"把 N 个任务一次性提交给线程池"。**这是错的**：

```python
# ❌ 一次性提交
for i, t in enumerate(tasks):
    if should_cancel(): break        # ← 只在开头检查
    futures[ex.submit(fn, i, t)] = i
for fut in as_completed(futures): ...
```

问题在于 `should_cancel` **只在最开始被检查一次**，之后所有任务都已经在队列里了。
而精析的成本闸门（"花费超过上限就停下问用户"）正是做在 `should_cancel` 里的 ——

> **⇒ 一次性提交会让用户设定的花费上限彻底失效，钱照花。**

改成**窗口化提交**：保持最多 `workers` 个在途，**每完成一个再补一个**，
每个提交点都过一遍闸门。

自测直接验证了这条（`t_budget_gate`）：

```
并发 3 路 / 每个任务花 1 元 / 门槛 3 元
实测：跑了 5 个就停（3 个在途 + 2 个补齐），花了 5 元
串行对照：精确在 3 个处停下
```

### 4.3 接入范围

| 位置 | 改动 |
|---|---|
| `screening.screen(workers=)` | 逐窗口并发；进度改按**完成数**报（并发完成顺序本来就不固定）|
| `pipeline.run` 精析段 | 候选并发；闸门做成"每次提交前检查"的回调 |
| `pipeline.Options.concurrency` | 默认 **1（串行）** |
| `settings.concurrency` | 默认 **1**；磁盘旧值（2，历史默认落盘）已重置 |
| 设置页「分析性能」 | 下拉 串行/2/3/4 路，带限流风险说明 |
| `analyze_dialog.options()` | 读回设置值 |

**默认串行**的理由：并发会同时发出多个请求，**更容易撞服务端限流**，
而限流的代价（指数退避等待）有可能比串行还慢。新功能不该默认改变所有老用户的行为。
