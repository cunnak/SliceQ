# v0.1.5 —— 深色界面

> 日期：2026-09-29｜需求：用户「为 sliceq 增加一个深色界面」
> 结论：**三档主题（跟随系统 / 浅色 / 深色）已实现**，界面颜色从 91 处硬编码
> 收敛为单一色板；自测 33 项 + 回归全过。

---

## 1. 改造前的现状（决定了改法）

先量了三件事：

| 事实 | 数据 | 影响 |
|---|---|---|
| `setStyleSheet` 调用 | **91 处，散在 9 个文件** | 颜色没有单一来源 |
| 不同的颜色值 | **只有 16 个**（出现 47 次） | 好消息：收敛成本可控 |
| `MUTED = "#888780"` 这类常量 | **在 6 个文件里各写了一遍** | 改一处漏五处 |
| 是否用过 `QPalette` | **完全没有** | ★ 深色做不成的根本原因 |

**最后一条最要紧**：有些控件**不吃 CSS** —— `QScrollBar` 的滚动条、
`QMenu` 的右键菜单、`QTableWidget` 的空白区、`QMessageBox`、`QToolTip`、
`QSpinBox` 的上下箭头……它们的颜色来自 **QPalette**。
只写样式表，深色界面上会到处露出浅色块。

另外：Qt 6.11 在 Windows 11 上默认 style 是 **`windows11`**（原生 Fluent 绘制），
**原生绘制的部分不理会 CSS** ⇒ 深色下必须换风格。

---

## 2. 三个决策（用户拍板）

| 问题 | 选择 | 说明 |
|---|---|---|
| 默认模式 | **跟随系统** | 设置页给手动切换；系统深浅变了自动跟 |
| 深色基调 | **中性深灰** | 窗口底 `#1e1f22`、面板 `#26282c`（不是纯黑） |
| 浅色外观 | **两种模式统一风格** | 浅色也改用 `Fusion`，换取"切换时观感不跳变" |

> ⚠️ 第 3 条是**有代价**的：浅色不再是"原生 Windows 外观"。
> 实测这个代价比预期小 —— 浅色与改造前的像素差异只有 **6~21/255**
> （因为按钮/输入框/表格这些主要控件本来就被 QSS 覆盖了）。

---

## 3. 实现

### 3.1 `sliceq/ui/theme.py`（新增，约 400 行）

- **`Palette` dataclass**：按**用途**命名的语义色（`muted` / `warn` / `danger`…），
  不是按颜色值。两套色值 `LIGHT` / `DARK`，字段必须一一对应（有自测守）。
- **`build_palette()`**：把色板翻译成 `QPalette`，**含 Disabled 组** ——
  不设的话 Fusion 会拿一套奇怪的灰去画禁用态。
- **`build_qss()`**：全局样式表。**刻意不覆盖** `QCheckBox::indicator` /
  `QComboBox::down-arrow` 这类**原生绘制的图形** —— 交给 `Fusion` + `QPalette`
  自动适配，手写 QSS 模拟反而容易画歪。
- **`color(key)` / `muted()` / `warn()` …**：取色接口。
  ⚠️ **必须"用到时再取"**，不能写成模块级常量（模块只 import 一次，
  切主题后值就永远停在旧主题了）。
- **`apply(app, mode)`**：设 style + palette + QSS。

**深色语义色统一提亮**（原来的值是为白底设计的，放深底上发闷）：

| 语义 | 浅色 | 深色 | 亮度 |
|---|---|---|---|
| muted | `#888780` | `#9a9da4` | 132 → 159 |
| ok | `#1d9e75` | `#2fbf8f` | 94 → 119 |
| warn | `#ba7517` | `#e0a44c` | 105 → 150 |
| danger | `#e24b4a` | `#f2625f` | 150 → 169 |
| accent | `#378add` | `#4c9eff` | 138 → 166 |

### 3.2 收敛 91 处硬编码

- 删掉 **19 个**重复的模块级常量（6 个文件）
- 替换 **67 处**引用为 `theme.xxx()`
- `sliceq/ui/` 下**硬编码颜色残留 0 处**（白名单只有两处，都写了理由：
  `theme.py` 自己是色板；`style_preview.py` 那块深色底板**刻意不跟主题** ——
  它模拟的是**视频画面**，不是窗口面板）

### 3.3 接线

- `__main__.py`：**创建窗口之前**应用主题（否则构造时求值的颜色会停在旧主题）
- `settings_page`：新增「外观」组（放最后 —— 模型接口/FFmpeg 才是必配项），
  只负责**发信号**
- `main_window`：接住信号 → 判断能不能切 → **落盘 + apply + 重建界面**

## 5. 过程中的坑（都留了注释）

### ① 设过样式表后，`app.style()` 返回的是**代理**
`setStyleStyle()` 之后 `app.style()` 变成 `QStyleSheetStyle`（**新对象**），
PySide6 下**没有 `baseStyle()`** 可以穿透 ⇒ 事后无法判断"Fusion 到底生效没有"。
**只能在 `setStyle` 之后、`setStyleSheet` 之前读一次记下来。**

### ② 第二次 `setStyle()` 不生效
因为 `app.style()` 已被 QSS 代理包住。**换 style 前要先 `setStyleSheet("")`**，
再设新样式表（同一函数内完成，中间不会渲染，看不到闪烁）。

### ③ 普通字符串变 f-string 时，QSS 的 `{}` 必须转义
`"…underline;}"` → `f"…underline;}}"`。
第一版脚本直接替换，造成 `f-string: single '}' is not allowed` 语法错误。
**顺序**：先转义原有花括号，再插占位符。

### ④ `@guard_ui` 装饰器被"抢走"（**犯了两次**）
在方法定义前插入新方法时，如果那个方法上面有装饰器，
装饰器会挂到**新方法**头上，原方法**丢掉异常兜底**。
⇒ 插在**装饰器之前**；插入后要检查一遍配对。

### ⑤ "先落盘、再问" ⇒ 设置已改但主题没切
设置页原本是先 `settings.set()` 再 emit。主窗口可能因"有任务在跑"**拒绝切换**，
于是下拉框退回了、设置里却已经是新值 —— **下次启动主题莫名变掉**。
⇒ 改成**先发信号，主窗口同意后才落盘**。谁做决定，谁负责记账。

### ⑥ 忙碌判据过宽 ⇒ 刚开程序换主题被拦
最初用 `pool.active_count() > 0`，而**启动时的环境体检也走这个池** ⇒
一开程序就被判定"正在分析"，弹窗拒绝。
顺带发现 `clips_page._worker` **跑完从不清空**（是"上一次的引用"而不是"是否在跑"）。
⇒ 新增语义明确的 `clips_page.is_analyzing()`，忙碌判据只看它和批量队列。

### ⑦ 探针自己的两个坑
- **offscreen 平台不加载任何系统字体**（`QFontDatabase.families()` 返回 0），
  中文全渲染成方块 ⇒ 截图没法看。办法：`addApplicationFont()` 直接注册
  Windows 字体文件（**只在这个探针里做**，产品运行时系统字体正常）。
- **baseline 组忘了重置 `QPalette`**，带着前一组的深色调色板去比，
  量出 218/255 的假差异。⇒ baseline 必须放在**所有主题干预之前**截。

## 7. 已知限制（如实记录）

| 项 | 说明 |
|---|---|
| 切主题时**不重建**独立对话框 | 导出/复制对话框是独立窗口，不受主窗口重建影响；但它们**不会**在已打开时跟着换肤。下次打开才是新主题。 |
| 有任务在跑时**拒绝**切主题 | 重建会清空进度显示。会弹窗说明并退回下拉框（不落盘）。 |
| 字幕预览底板**不跟主题** | 刻意的：它模拟视频画面（白/黄字幕压在什么底色上），浅色主题下也保持深色。 |
| 深色的对比度**未做无障碍审计** | 只保证了"语义色在深色下更亮"，没算过 WCAG 对比度比值。 |
| 只测了两个页面 × 两种模式 | 渲染判据覆盖「任务」「设置」；候选清单/字幕样式页只在探针里人工看过。 |
