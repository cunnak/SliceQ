## 三、本轮抓到的四个真缺陷

### 3.1 `add_clip` 静默吞键 → 数据无声丢失 🔴

`store.add_clip(**kw)` 用 `kw.get()` 取值，**不认识的键被静默忽略**。
而 `pipeline` 传的是 `kind=` / `title=`，表里的列名却是 `type` / `title_hint`，
且 `hint` / `confidence` **根本没有对应的列**。

后果：三个字段全部写不进去，**没有任何报错**。

**修法**：签名改成显式关键字参数（传错立刻 TypeError）+ 加 v3 迁移补两列。

### 3.2 断点续跑"续了但不省钱" 🔴

`pipeline` 只在**回调层**做了缓存（不重复写盘），但 `screening.screen`
并不知道哪些窗口已完成 —— 于是**每次重跑仍会对所有窗口调用模型**。

后果：用户以为"续跑省钱"，实际每一分钱都重花了一遍。

**修法**：`screen(..., skip_windows=set)`，真正跳过已完成的窗口。

### 3.3 缓存命中时重复计费 🔴

`refine_one` 命中缓存后返回的是**缓存里存的历史 usage**，
导致"重跑一次，花费翻倍"——而**实际一分钱没花**。

更麻烦的是它会撞上硬上限：用户重跑几次，明明没花钱，
却被"已超上限"拦住。

**修法**：缓存命中返回 `Usage()`（本次无真实调用 = 本次消耗为 0）。

### 3.4 硬阀把短视频砍光 🟠

纯按比例算预算：12 秒素材 × 20% = **2.4 秒**，
任何合理候选（几秒到几十秒）都会被砍掉，用户看到"0 个候选"。

**修法**：`budget = max(duration × ratio, 120 秒)`。
比例是长视频的约束，**绝对下限是短视频的保护**。

> 这四个都属于同一类：**每一个环节单独看都成功，端到端结果是错的**。
> 而且没有一个会报错。

## 四、设计要点（实现里落成注释的）

| 点 | 做法 | 为什么 |
|---|---|---|
| **时间基准** | 写死在 `screen_prompt` 内，不通过参数传 | 这种前提一旦可选，就一定会有人忘传 |
| **越界校验** | 解析候选时丢弃落在窗口外的时间戳 | 防"模型算错基准导致整体偏移"，唯一手段 |
| **拼贴抽帧** | 16 帧拼成一张图，而非逐帧送 | 逐帧 3 小时要 360~1080 次调用；拼贴后只需 20 张左右 |
| **确认点不走跨线程弹窗** | 第一次 run 停在粗筛后，用户点继续时第二次 run（缓存全命中） | 跨线程等待弹窗容易死锁；这样每步都落盘可续 |
| **step 信息编码** | `progress` 描述加 `[stage]` 前缀 | Worker 的 progress 信号只有 `(int,int,str)`，不带就丢阶段信息 |
| **状态只在变化时写库** | `_last_status` 比对 | 进度回调一次来几十上百次，每次都 UPDATE 没必要 |
| **预览用 `-c copy` 切副本** | 失败退回重编码 | 内置播放器（QtMultimedia）编解码支持不一致，出问题还不报错 |
| **重新分析先清旧切片** | `store.clear_clips()` | 否则新旧结果堆在同一张表里，用户看到"两次结果叠加" |

### 5.2 三个真问题（都已修）

**① 媒体字段名必须按类型分派** 🔴

粗筛送的是**拼贴 PNG**，但 `build_http_messages()` 一律用 `video_url` 发出：

```
HTTP 400  InternalError.Algo.InvalidParameter: Invalid video file.
```

**这条错误信息完全没提示"字段名错了"** —— 它说"视频文件无效"，
会让人以为是文件损坏或编码有问题，而不是"你用了视频字段传图片"。

修法：按 MIME 分派 —— `image/*` → `image_url`，其余 → `video_url`。
`build_dashscope_messages()`（通道 A）同理，key 选 `image` / `video`。

**② `_endpoint()` 把路径拼了两次** 🔴

改 SNI 绕行那段代码时引入的：常规分支拿 `urlparse(base_url).path` 去拼 `base_url`，
而 base_url 里已含路径 ⇒

```
https://dashscope.aliyuncs.com/compatible-mode/v1/compatible-mode/v1/chat/completions
→ 404（空 body，看不出原因）
```

修法：常规分支直接用 `base_url`，只有绕行时才重组。

**③ 粗筛不该开思考** 🟠

实测同一输入：

| 模式 | output_tokens | reasoning_tokens | 正文 |
|---|---|---|---|
| `auto` | 207 | **202（97%）** | `[]` |
| `off` | **2** | 0 | `[]` |

**输出 token 差 100 倍**，而粗筛要的只是"快速判断"。
开着思考既慢又贵，还多一层"思考把正文挤光"的风险。
⇒ `screening.screen()` 固定 `thinking="off"`。

### 5.3 端到端实测（90 秒直播片段）

```
粗筛产出：0.0→46.0s  置信 95  [frame]  "情绪激动吐槽扫码支付，含脏话"
★ 确认点触发 → 精析报价 ¥0.0100
精析产出：0.0→21.0s  ［观点］score=55  "扫码支付乱象"
          理由："画面全程为地板无信息量，且内容包含大量违规脏话，不适合发布。"

实际花费 ¥0.0071（启动时上限 ¥0.14）    总耗时 22 秒
token: in=8222 out=176 reasoning=0
```

**质量观察**：
- 粗筛定位准确 —— 与本地转录内容（"拿个二维码过来叫我扫着"）吻合
- **精析不只看声音，还看画面**（发现"画面全程为地板"）—— 音视频联合理解确实生效
- 精析给出的 `score=55` + "不适合发布"的结论**是有用的**：
  它比"给个高分"更有价值，用户可以直接跳过这一段

### 5.4 多窗口规模化验证（22 分钟 / 3 个窗口）

```
转录：跳过静音 59s，剔除重复 29 段
粗筛：3/3 个窗口完成 → 候选 5 段
确认点触发 → 报价 ¥0.0700
精析：5/5 段完成
总耗时 178.2s    实际花费 ¥0.0469（启动时上限 ¥0.22）
token: in=56174  out=737  reasoning=0
```

**精析质量（值得单独看）**：

| 片段 | 评分 | 精析给出的判断 |
|---|---|---|
| 0.0→27.0s | **10** | 黑屏废片 —— "全程黑屏，无有效画面信息，无法作为切片发布" |
| 374→462s | 45 | "镜头对着水桶和地板，无有效人物画面" |
| **768.5→809.5s** | **85** | **"他们不是小资，是蠢"**（观点 · 痛批眼界狭隘）|
| 901→967s | 50 | "画面全程拍腿和机箱，无主播露脸，纯音频无法发布" |
| 1236→1247s | 45 | 直播事故现场 —— "前 38 秒摄像头关闭，后 11 秒镜头怼腿" |

**两个观察**：

1. **评分是有区分度的**，不是"都给高分"。85 分那条确实是可用的金句；
   低分那几条给的**理由具体、可核对**（黑屏 / 拍地板 / 怼腿），不是空泛评价。

2. **它识别出了一个用户真正需要的信息：哪几段的画面是废的。**
   素材是竖屏直播，主播有时把摄像头对着别处 —— 这类问题**剪辑时才会发现**，
   而那时已经白剪了一遍。精析提前把它标出来，
   用户可以直接跳过，**这比"只找高光"更有实用价值**。

**成本外推**：22 分钟 ¥0.0469 ⇒ **3 小时约 ¥0.38**
（KR3 要求 ≤¥1，**达标**；预估值 ¥0.53 是保守上限，实际约为其 72%）。

### 5.6 一次"看起来像 bug 实际不是"的情况

第一次跑真实流水线（用 `source.mp4`）返回 **0 个候选**，一度怀疑是思考把输出挤光了。

诊断后发现：**该素材整段 12 秒的转录只有 `by bwd6`**（视频末尾水印被识别成语音），
**根本没有内容**。模型返回 `[]` 是**正确判断**。

> 判据：`finish_reason` 是 `stop`（正常结束）而非 `length`（被截断），
> 且 `thinking=off` 时同样返回 `[]` ⇒ 不是被挤掉，是真的没有。
>
> **教训**：测试素材本身要有内容，否则会把"正确答案"误判成缺陷。
> 用合成素材（`testsrc2` 彩条、`source.mp4`）测"效果"是无效的 ——
> 它们只能测"链路通不通"。
