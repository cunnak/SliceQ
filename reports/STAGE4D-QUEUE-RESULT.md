## 0. 先说结论

| 事项 | 结论 |
|---|---|
| 转录阶段并发 | **实测否决，不做**。GPU 上 4 路比串行**慢 43%**，2 路只有 1.12× 却把显存从 5.2G 推到 7.1G |
| CPU 路径转录并发 | **未完成实测**（如实记录，见 §1.3）。决策不依赖它 |
| 多录像任务队列 | **已完成**：任务页多选入队、串行执行、失败隔离、不持久化 |
| `concurrency` 设置 | 明确只作用于**粗筛/精析**，界面上已注明 |
| 顺带修掉的既有缺陷 | **3 个**（§5）：状态落库写错层次 / 短幻觉逃过治理 / 删任务清不干净（schema v5）|

> 这一阶段最值得留下的不是代码，是**把"看起来该做的优化"量过一遍再决定**。
> 转录并发是 TASKS 原文写着的需求，直觉上"多核并发当然更快"——
> 实测把它否掉了。
>
> 另一件值得记的是：**做新功能时被照出来的老问题，往往比新功能本身更有价值**。
> 三个缺陷有两个（状态落库、短幻觉）都是"单任务路径下完全正常，
> 只有换一条路径才暴露"——而它们都**不报错**。

## 1. 前置实测：转录分片并发到底有没有收益

### 1.1 方法

从真实录播切 4 片等长（180s）音频，**走产品代码** `asr.transcribe_chunk()`
（不是另写一套实验代码 —— 那样测不到真实开销），对比三种并发度：

- 串行 1 路（现状）
- 并发 2 路
- 并发 4 路

每个场景记录：墙钟、单片耗时、段数、**文本 md5**（验证结果是否一致）、
显存峰值（后台 `nvidia-smi` 采样）。

### 1.2 数据

环境：RTX 4060 Laptop 8GB（**已占用 3.3GB**，剩约 4.9GB）、
`ggml-large-v3-turbo.bin`、ffmpeg 9.0.2 full_build。

| 场景 | 墙钟 | 加速 | 显存峰值 | 单片耗时（秒） |
|---|---|---|---|---|
| 串行 1 路 | 82.66s | 1.00× | 5209 MB | 23.3 / 21.7 / 21.3 / 16.5 |
| 并发 2 路 | 73.75s | **1.12×** | 7106 MB | 66.5 / 24.1 / 28.5 / 21.2 |
| 并发 4 路 | 144.16s | **0.57×** | 7541 MB | 144.2 / 122.5 / 135.4 / 92.9 |

**结果一致性**：三个场景的文本 md5 **完全相同**（`7c4790512a49`），
段落数也完全一致（68 / 66 / 72 / 76）。

> 这一条同样重要：**并发不改变结果**，所以它带来的只有代价，
> 没有质量上的好处可以拿来抵消。

### 1.3 三条认识

**① GPU 的计算单元是共享的，并发不增加总算力。**
whisper 本身就是 GPU 密集型。多个进程只是把同样的计算摊开，
还要额外付出上下文切换与显存换页。总计算量不变 ⇒ 墙钟不会按并发度下降。

**② 显存是硬约束，不是余量。**
2 路就把峰值推到 7106MB。在 8GB 卡上，用户同时开着游戏/浏览器
（本机环境就已经被占了 3.3GB）就 OOM 了。
**为 12% 的收益去赌一个 OOM 风险，不划算。**

**③ 单片耗时反而变长，说明瓶颈换了。**
并发 4 路时片 0 从 23s 变成 144s —— 这不是"这片变难了"，
是四个进程在互相拖。**当并发让单体变慢 6 倍时，总时间不可能赢。**

### 1.4 于是决定：转录固定串行

`concurrency` 设置（设置页「分析性能」）**只作用于粗筛/精析**，
那里是网络 IO 密集，并发确实有意义（4-C 已完成）。
设置页与 `pipeline.Options` 的说明都补了这一点。

> **把"为什么不做"写进文档**，与"做了什么"同等重要 ——
> 否则下一个接手的人看到 TASKS 里"转录并发度可配置"，
> 会重新实现一个已经被数据否决过的东西。

## 2. 多录像任务队列

### 2.1 需求对应

TASKS 验收标准原文：**「两条录像批量入队，顺序完成，无限流报错」**。

### 2.2 实现

| 文件 | 内容 |
|---|---|
| `sliceq/ui/queue.py` | `QueueItem` / `run_queue()` / `AnalysisQueue` |
| `sliceq/ui/pages/tasks_page.py` | 表格改多选、`加入队列` 按钮、队列面板、状态列同步 |
| `sliceq/ui/main_window.py` | 持有队列实例、关窗保护 |
| `sliceq/ui/pages/clips_page.py` | `_run_analysis` → **公开 `run_analysis`**（队列复用它，不复制逻辑） |

**为什么把 `run_analysis` 提为公开**：队列不该复制一份"构造 transport +
决定确认点"的逻辑。两份实现迟早漂移，而漂移的后果是
「单任务和队列跑出来不一样」—— 这种缺陷最难被发现，因为两条路径
单独看都正常。

### 2.3 三个关键设计决策

**① 队列串行** —— 理由就是 §1 的实测。多条录像同时跑是负收益。

**② 队列不持久化**（关程序清空）：

1. 持久化就必须回答"上次退出时正在跑的那条算什么状态"，
   而真相是"跑到一半"—— 既非完成也非未开始；
2. 代价很低：pipeline 有断点续跑（转录分片缓存 + 粗筛窗口缓存），
   重开程序再点一次分析，跑过的部分不重复花钱；
3. 不持久化反而更好懂 —— 下次打开看到"有 2 个在排队"却没在跑，更困惑。

界面队列面板底部有一行常驻说明写这件事。

**③ 路径在执行时现取**，不在入队时快照 `source_path`。
否则会出现"入队时文件还在、真跑到时已被移走"的过期快照。
（自测里有一条专门验证：入队后改名，执行时用的是库里的新名字。）

### 2.4 三条边界行为

| 场景 | 行为 | 理由 |
|---|---|---|
| 某条抛异常 | 记失败，**继续下一条** | 与 `export_clips` 同样取舍。三条排着，第一条文件损坏不该让后两条也不跑 |
| 用户点了取消 | **整队停**，剩余标 `skipped` | 「我不想跑了」与「这条本身出错」是两回事 |
| 源文件不在了 | 入队前就剔除并告知；执行时兜底再判一次 | 排到一半才发现文件没了，是最差的结果（前面已经跑完了） |

## 3. 界面上的两个细节（都是"看起来对但会咬人"）

### 3.1 状态列同步不能重建表格

队列跑的时候，任务表的状态列要跟着变（转录中 → 粗筛中 → …）。
最直接的做法是调 `refresh()` —— 但它会 `setRowCount(0)` 重建整个表格，
于是：

- 用户的多选被清掉（**队列跑着时他很可能正在挑下一批**）；
- 滚动位置弹回顶部。

改为 `_sync_table_status()`：按 task_id 找到行、**只改第 3 列文本**，
并按 1.2s 节流（进度信号很密）。
自测里专门验了"行数不变、task_id 顺序不变、用户选择还在"。

### 3.2 关程序要先拦一下

队列在跑时关窗口 = 中断一条流水线。原来的 `closeEvent` 只
`pool.wait(3000)` 然后走人 —— 进程被强杀会留下"状态是 refining
但实际没在跑"的任务，用户下次打开会一头雾水。

改为：弹确认 → 用户选「否」则 `event.ignore()` → 选「是」才
`cancel()` + `wait(8000)` 给取消检查点一点时间。

## 5. 顺带发现并修掉的三个真实缺陷

三个都不是队列本身的 bug，而是**做队列时被照出来的既有问题**。
它们的共同点：**不报错、只在特定路径下显现**。

### 5.1 任务状态落库写在了 UI 回调里（层次错误）

`store.set_task_status` 原先全写在 `clips_page` 的三个 UI 回调里：

    _on_progress → 阶段状态（转录中/粗筛中/精析中）
    _on_done     → 待精析 / 待导出
    _on_error    → 出错

队列走的是 `run_analysis`（模块级函数，直接调 `pipeline.run`），
**不经过这些回调** ⇒ 队列跑完，任务状态**永远停在「已导入」**，
而且**不报任何错**。

> 端到端第一次跑出来就是三条 FAIL：`状态落库为待导出 — imported`。
> 如果没有这个 e2e，这个缺陷会一直躺在代码里 ——
> 单任务路径一切正常，只有走队列才暴露。

**修法**：状态是**任务的属性**，该由**执行者**维护，不该由**显示者**维护。
把它下沉到 `pipeline.run()`：

- `report()` 里按阶段写状态（`_STAGE_STATUS`，只在变化时写库）
- 两个返回点分别写 `ready` / `screened`
- 新增 `run()` 包装层：异常写 `error`、取消写 `cancelled`
- `clips_page` 里那几处**全部删掉**（避免两处都写、互相覆盖）

同时顺手修了一个语义错误：**取消原来被写成 `error`**。
用户按了取消然后看到"出错"，会以为程序坏了。
新增 `STATUS_CANCELLED = "cancelled"`（标签「已取消」）单独表示。

验证：`selftest_pipeline_status.py`（16 项）覆盖四条路径 ——
正常 / 异常→error / 取消→cancelled / **落库本身失败不能拖垮分析**。

### 5.2 短幻觉完全逃过治理（真实数据暴露）

端到端里发现：某条任务**产出 0 条切片**。查下去发现转录文本长这样：

    1. [  5.9] 感谢观看
    2. [ 17.7] 感谢观看
    3. [ 20.6] 感谢观看
    ...
    15. [ 50.0] 感谢观看
    16. [ 58.9] 感谢观看
    17. [ 64.8] 优优独播剧场——YoYo Television Series Exclusive

三层幻觉治理**一处都没拦住**，三个具体缺口：

| 缺口 | 原因 |
|---|---|
| `感谢观看`（4 字）重复 5 次 | `_REPEAT_MIN_LEN = 8` ⇒ **根本不参与判重** |
| `优优独播剧场…` | 特征词表里没有这个模板（它是电视台用语） |
| 词表里有 `谢谢观看` 却没有 `感谢观看` | 一个字之差 |

**修法（保守优先）**：

1. **判重门槛分两档**：长句（≥8 字）重复 3 次即判；
   **短句（4~7 字）需要 5 次**。
   短句不能直接套 3 次 —— 真实口语里"我知道了"重复 3 次完全可能。
   抬高到 5 次后，客观判据（"真实讲话不会逐字重复 5 遍"）仍然成立。
2. **低于 4 字的极短句一律不判** —— "好/啊/对"重复是正常的。
3. 特征词表补 `独播剧场`。
4. **故意不加 `感谢观看` 到词表** —— 主播下播时真会说这句话，
   按词删会误杀。它走重复判据（有客观依据），不走词表猜。

**实测效果**（同一段素材、同一份转录）：

    素材2 的粗筛候选  0 条 → **1 条**（幻觉清掉后，粗筛才看得到真实内容）
    素材2 的转录段数  28 → 22

> 这条的价值不只是"少了几句废话"：**粗筛是基于转录文本判断的**，
> 文本被幻觉污染时它会判定"无价值" —— 用户因此拿不到本该有的切片。
> 幻觉治理不只是字幕质量问题，它**直接影响产出**。

验证：`selftest_hallucination.py`（26 项）。重点是**双向验证** ——
既要求"该清的清了"，也要求"不该清的**一条都不能少**"：
极短应答词、真实口语重复 3 次、一段正常内容零剔除。
> 只测"幻觉被清了"是不够的：把门槛降到 2 次也能让那些断言通过，
> 代价是删掉主播真说的话 —— 而**删掉的内容不会有人发现**。

### 5.3 删任务清不干净（隐私 + 膨胀）

清理测试残留时发现：删掉 14 个任务后，`transcript_seg` 表里
**还剩 659 行**。查下去是建表时漏了外键：

```sql
-- 其它 4 张子表都有：
task_id INTEGER NOT NULL REFERENCES task(id) ON DELETE CASCADE
-- transcript_seg 只有：
task_id INTEGER NOT NULL
```

`delete_task()` 只有一句 `DELETE FROM task` —— 级联全靠外键，
**漏一张表就漏一份数据**。

**为什么这个比"数据多一点"严重**：

- **隐私**：用户删任务的意思是"这些素材我不要了"，
  但素材里**说过的话还留在库里**
- 数据无上限膨胀：转录是几 MB 文本，每次分析都写

**修法**：schema **v5** 迁移 —— SQLite 不支持 `ALTER TABLE` 加外键，
只能重建表，顺便把已产生的孤儿行清掉。

**验证**（`selftest_store_integrity.py`，10 项）：

- 从 schema 里**动态**查出所有引用 `task(id)` 的表（不写死列表 ——
  写死的话将来加新表就漏了），逐张检查 CASCADE
- 逐张**实测**级联删除（不是只读 DDL 文本）
- 三处断言加了"集合非空"前置

> ⚠️ 最后这条不是多余的：第一版测试因为模式匹配写错（去了空格却拿
> 带空格的模式比对），返回了**空的表清单**，于是
> "所有表都没有孤儿""所有表都被清空"**全部假通过** ——
> `all([])` 恒为 `True`，**空集合上的全称断言永远成立**。

## 6. 已知限制（如实记录）

| # | 限制 | 说明 |
|---|---|---|
| R28 | **未达门槛的幻觉会保留** | 单次短幻觉（`感谢观看`×1、`多謝`×1）、长句重复 1~2 次。**这是刻意的保守取舍**：没有"重复"作客观判据时，只能靠词表猜，而误杀真话的代价更大。e2e 会把这类残留打印出来 |
| R29 | **粗筛缓存没有内容指纹** | `screen.jsonl` 按窗口号缓存，不校验"转录文本是否变过"。改了 ASR 逻辑后重跑分析，会拿**新转录**配**旧粗筛缓存**。当前影响可控（转录每次都重算，粗筛结果是超集），但属设计缺陷 |
| R30 | **多进程同时写库会出错** | 压测时（5 个进程并发读写）出现过一次 `attempt to write a readonly database`。单进程正常。SliceQ 是单实例应用，但如果用户开两个实例，可能撞上。需要 `busy retry` 或单实例锁 |
| R31 | **CPU 路径的转录并发未实测** | 见 TECH-DESIGN §5.6：决策不依赖它（不为慢路径增加复杂度），但要区分"实测"与"推理" |

---

## 7. 不做什么（也要写清楚）

| 项 | 为什么不做 |
|---|---|
| 转录并发 | 实测负收益（§1）。**不是遗漏，是被数据否决** |
| 队列并行执行 | 同上。想快点应该调单条任务内部的并发 |
| 队列持久化 | 语义说不清 + 断点续跑让代价很低 + 不持久化更好懂（§2.3） |
| 把 `感谢观看` 加进特征词表 | 会误杀主播真说的话。走重复判据更稳 |

> **把"不做"和"为什么不做"一起写下来**，与"做了什么"同等重要 ——
> 否则下一个接手的人看到 TASKS 里写着"并发度可配置"，
> 会重新实现一个已经被数据否决过的东西。
