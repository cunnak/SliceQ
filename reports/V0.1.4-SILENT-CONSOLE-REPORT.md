# v0.1.4 —— 让 SliceQ 运行时不再闪出终端窗口

> 日期：2026-09-29｜触发：用户报「能不能在 SliceQ 运行时将弹出的终端静默运行」
> 结论：**根因已定位并修复，真机 A/B 对照通过**（旧版 6 个窗口 → 新版 0 个）
> 相关：`sliceq/subproc.py`（新增）、`selftest_subproc_flags.py`（新增）、
> `probe_console_flash.py` / `probe_no_window_e2e.py` / `probe_exe_console_compare.py`（取证）

---

## 1. 现象

SliceQ 运行时会**闪出终端窗口**。用户能看见，但一闪而过，抓不到、截不了图。

---

## 2. 根因

**父进程是 GUI 子系统（无控制台）时，启动 console 子进程会让 Windows
为它创建一个控制台宿主窗口。**

- `SliceQ.exe` 由 PyInstaller `--windowed` 打包 ⇒ `SliceQ.spec: console=False`
  ⇒ **PE 子系统 = GUI（2）**、**没有控制台**（实测 `GetConsoleWindow()` 为 0）
- `ffmpeg.exe` / `ffprobe.exe` 是 **console 子系统**（PE `Subsystem=3`）
- Windows 的 `CreateProcess` 在这种组合下**分配一个新的控制台** ⇒ 屏幕上的终端窗口

窗口类名实测为 **`CASCADIA_HOSTING_WINDOW_CLASS`** ——
Win11 的控制台宿主（Windows Terminal 的内核窗口）。这与用户描述的"终端"
完全吻合。

### 2.1 关键反直觉点：**重定向救不了**

本项目原本 **19 处子进程调用全部都有重定向**（`capture_output=True` /
`stdout=PIPE`），照样会弹。四轮对照实验（`probe_console_flash.py`）：

| 启动方式                      | 3 次启动中触发窗口 |
|------------------------------|------------------|
| 管道 + 不加 flag（**原状**）    | **3 / 3** ★ 每次都弹 |
| 管道 + `CREATE_NO_WINDOW`     | **0 / 3** ✅ |
| 管道 + `DETACHED_PROCESS`     | **0 / 3** ✅ |
| `DEVNULL` + 不加 flag          | **3 / 3** ★ 光重定向没用 |

⇒ 必须**显式**告诉 Windows「别分配控制台」，靠重定向"顺带避免"是不成立的。

---

## 3. 为什么前两轮排查没发现（**这一节比结论更重要**）

### 3.1 第一轮：轮询式探针 → 误判"不弹"

`probe_console_window.py` / `probe_console_handles.py` 用的是
**「启动子进程 → 睡 2 秒 → `EnumWindows` 找窗口」**。
结果四组、六组组合**全部显示"不弹"**。

原因：这些窗口**存在时间极短**（几十毫秒~数秒），轮询的采样间隔是
**百毫秒~秒级**，必然漏掉。

⇒ **用轮询去检测"一闪而过"的东西，得到的"没有"是假阴性。**

### 3.2 第二轮：模拟环境不纯粹 → 又一次误判

改用 `pythonw.exe`（GUI 子系统解释器）后仍然"不弹"，原因是
**从 bash 启动的进程，标准句柄被接成了管道**（实测 `stdout = 0x2d0`）——
而"双击 exe"的真实 GUI 进程，三个标准句柄都是 `NULL`
（用 `SetStdHandle(-10/-11/-12, NULL)` 手工复现才对齐）。

### 3.3 第三轮：换 `SetWinEventHook` → 立刻抓到

`probe_console_flash.py` 用 **`SetWinEventHook(EVENT_OBJECT_CREATE)`**，
事件驱动、**不会漏**，第一次跑就抓到 4 个窗口事件。

> **教训**：检测"瞬时现象"要用**事件**，不能用**轮询**。
> 前两版探针报的"不弹"是**假阴性**，而我在上面多花了两轮才意识到。

---

## 4. 修法

### 4.1 统一入口（而不是逐处加参数）

新增 `sliceq/subproc.py`：

```python
CREATE_NO_WINDOW = 0x08000000        # Windows：不分配控制台

def effective_flags(explicit=None) -> int:
    if os.name != "nt":      return 0
    if explicit is None:     return CREATE_NO_WINDOW   # 默认静默
    return explicit                                    # 显式传入则尊重

def run(args, **kw):   return subprocess.run(args,  **_apply(kw))
def popen(args, **kw): return subprocess.Popen(args, **_apply(kw))
```

**19 处调用点全部改走它**（12 个文件）。`bridge.py` 启动 VideoCaptioner
要 `DETACHED_PROCESS`，显式传参即被尊重。

**为什么不用"逐处加 `creationflags=`"**：本项目已**两次**栽在
"在 N 处修了、漏了第 N+1 处"——
① 子进程管道排空（`editor.py` 修了、`asr.py` 漏了 ⇒ 死锁）
② 进度回调 `with_progress=True`（7 处传了 6 处 ⇒ 进度条永不动）
同一个形状：**改法对、覆盖不全**。所以改成唯一入口 + 静态检查兜底。

### 4.2 静态检查（防漏）

`selftest_subproc_flags.py`：
- **A 静态**：`sliceq/` 下不得出现裸 `subprocess.run(` / `subprocess.Popen(`
  （唯一豁免 `subproc.py` 自己）
  ★ 含**对照组**：喂一段旧的裸调用源码，检查必须报出来（否则测试没牙）
- **B 行为**：`subproc.run/popen` 真的注入了 flag；显式 flags 被尊重
- **C 真跑**：静默化后 stdout/stderr 各 200KB 完整、退出码透传、
  `TimeoutExpired` 仍抛

**16/16 通过。**

## 5. 验证（三层，全部有对照）

### 5.1 输出完整性（怕"修一个问题换一个"）

`probe_no_window_output.py`，5 个用例对比加/不加 flag：

| 用例 | stdout | stderr | 结论 |
|---|---|---|---|
| silencedetect（大 stderr） | 0/0 | 1009/1009 | 一致* |
| 大 stdout（3MB JSONL） | 2700000/2700000 | 6/6 | 逐字节相同 |
| 中文与多行输出 | 21/21 | 57/57 | 逐字节相同 |
| ffprobe JSON | 96/96 | 0/0 | 逐字节相同 |
| ffmpeg -filters | 41986/41986 | 0/0 | 逐字节相同 |

\* 「逐字节不同」的是 ffmpeg 打印的**内存地址**（`@ 0000000000812e40`
vs `@ 0000000000820a40`）—— `probe_silencedetect_determinism.py`
做了对照：**两次都不加 flag 也会不同**，属 ffmpeg 自身非确定性；
真正要解析的 `silence_start/silence_end` **完全一致**。

> ⚠️ 顺带记一个测试陷阱：**ffmpeg 的 stderr 含进程内存地址，
> "逐字节比对"对它是无效判据**，会假阳性。

### 5.2 业务链路（走真实函数）

`probe_no_window_e2e.py`，用产品自己的函数，**并带对照组**：

```

[OK] ffmpeg_tools.probe_video_size()

A 对照组（旧写法·裸 subprocess）  事件数: 3   ← 证明钩子有牙
B 修复后（走 subproc 统一入口）   事件数: 0   ← 证明修复有效
```

### 5.3 ★ 真机 A/B（最有说服力）

## 6. 过程中自己踩的两个坑（都值得记）

### 6.1 模块名 `proc` 与局部变量撞名 ⇒ 运行时崩溃

第一版模块叫 `sliceq/proc.py`。而 `asr.py::_run_ffmpeg` 里原本有：

```python
proc = subprocess.Popen(...)      # 局部变量，就叫 proc
```

批量替换后变成 `proc = proc.popen(...)` —— **自我赋值**，
Python 于是把 `proc` 视为局部变量 ⇒ 右侧引用未绑定 ⇒
`UnboundLocalError: cannot access local variable 'proc'`。

**为什么危险**：它**只在运行到那一行时才炸**，静态检查、
导入冒烟、gui 自测都发现不了（`asr.py:156` 与 `editor.py:204` 两处）。
第一次端到端跑才暴露。

**修法**：模块改名 **`proc` → `subproc`**（`proc` 是极常见的局部变量名，
撞名风险太高），同时修掉那两处调用。

### 6.2 验证脚本自己写错，白判了一次"钩子失效"

`probe_no_window_e2e.py` 里 `phase` 是列表 `["准备"]`，回调读 `phase[0]`；
但 worker 里写了 `global phase` + `phase = "A_..."` —— **重绑成字符串**，
于是 `phase[0]` 变成 `'A'`，`count_in("A_对照组(裸调用)")` 恒为 0。

结果：**明明抓到了 3 个事件，却输出"钩子失效，本结果无效"**。
（原始 `events` 列表里事件一直都在。）

**教训**：**统计口径写错，会把"通过"判成"失败"** —— 与"对照组失败同样是信号"
属于同一族：结论异常时，先怀疑度量本身，再怀疑被测对象。
