# v0.1.1 热修复报告：卡在「准备中…」

> 日期：2026-09-28｜触发：v0.1.0 发布后第一个真实缺陷
> 现象：用户选了一个视频点「开始精析」，界面**一直停在「准备中…」不动**
> 结论：**其实是三个独立缺陷叠在一起**，两个是"改过 N 处、漏了第 N+1 处"

---

## 0. 用户看到的现象

- 候选清单页的进度条恒为 0，标签一直是「准备中…」
- 表格里"还没有片段"
- 任务表格里那条任务的状态是「转录中」

## 1. 取证过程（先看软件自己写了什么）

| 步骤 | 结果 |
|---|---|
| 读 `%APPDATA%\SliceQ\logs\sliceq.log` | **只有 2 行启动记录，没有任何错误** |
| 读数据库 `task` 表 | `status = transcribing`，`created_at = 20:36:05` |

> 库是 WAL 模式，只拷主文件会得到空表（这个坑本项目踩过第二次了）。

## 2. Bug 1（真·卡死）：子进程管道死锁

### 2.1 根因

`sliceq/asr.py::_run_ffmpeg` 当时是这样：

```python
proc = subprocess.Popen(args, stdout=PIPE, stderr=PIPE)   # 开了两个管道
while True:
    if proc.poll() is not None: break      # ← 循环里一个字节都不读
    time.sleep(0.4)
out, err = proc.communicate()              # ← 等进程结束后才开始读
```

子进程把管道缓冲区写满（Windows 上约 **64KB**）后**永久阻塞在写上**，
而父进程在等它退出 —— **互相等，永远不动**。
表现就是：进程活着、**CPU 0%**、不报错、不结束。

### 2.2 实测证据

把那条命令**单独跑一遍**（同样的 84 分钟音频）：

```
用时          : 0.8 秒          ← 本该 0.8 秒就完
退出码        : 0
stdout 字节   : 0
★ stderr 字节 : 95,662          ← 超过 64KB 管道缓冲区
```

**95,662 > 65,536** ⇒ 必然死锁。静音段越多，stderr 越大。

**为什么 100+ 项自测全过却没抓到**：是否超缓冲区取决于**素材的静音段多少**。
之前的测试素材没这么多静音，所以从没触发。
⇒ 典型的**"只在真实用户素材上发作"**的缺陷。

### 2.3 修法

```python
while True:
    try:
        out, err = proc.communicate(timeout=0.5)   # ★ 等待期间持续排空两个管道
        return CompletedProcess(args, proc.returncode, out, err)
    except subprocess.TimeoutExpired:
        if should_cancel and should_cancel(): ...   # 取消仍然有效
        if time.time() - t0 > timeout:     ...      # 超时仍然有效
```

`communicate(timeout=...)` 会用**后台线程并发读两个管道**；超时抛
`TimeoutExpired`，但**已读到的数据不会丢**，可以继续 `communicate`。

⚠️ **第 458 行那条 whisper 转录更危险** —— 它的 stdout 是 JSONL，**动辄几 MB**，
同样会堵。`_run_ffmpeg` 是 5 个调用点的公共入口，改这一处全修。

### 2.4 ★ 同一个坑，项目里已经修过一次

`editor.py::_run_ffmpeg` 的注释白纸黑字写着：

> "ffmpeg 写满管道缓冲区后会永久阻塞 —— 表现为「卡住不动」，
>  而且不会有任何报错。这里把 stderr 导到临时文件，两边都不堵。"

**`editor.py` 修了，`asr.py` 漏了。** —— "在 N 个地方修了、漏了第 N+1 个"。

## 3. Bug 2（进度永远不动）：漏传 `with_progress=True`

### 3.1 根因

`WorkerPool.run(..., with_progress: bool = False)` —— `progress` 这个 kwarg
**只有 `with_progress=True` 时才由 `Worker` 注入**。

`clips_page._kickoff`（手动单条分析）**没传**：

```python
self.pool.run(run_analysis, ..., on_progress=self._on_progress, ...)
#                                     ↑ 没有 with_progress=True
```

⇒ `run_analysis(..., progress=None)` ⇒ `on_prog` 里 `if progress:` 为假
⇒ **整条进度链断掉**，进度条恒 0、标签永远「准备中…」——**完全不报错**。

### 3.2 关键证据

全项目 **7 处** `pool.run` 调用点，**6 处都传了**：

```
copy_dialog.py:128    ✓        export_dialog.py:522   ✓
settings_page.py:435  ✓        settings_page.py:510   ✓
tasks_page.py:471     ✓        queue.py:348           ✓   ← 队列那条路是对的
clips_page.py:216     ✗  ← 只有这里漏了
```

所以：**从队列跑有进度，手动单条跑没进度。**

### 3.3 修法 + 怎么防复发

补上 `with_progress=True`，并加**静态检查**（`selftest_pipeline_wiring.py`）：
扫所有 `pool.run(...)`，**出现 `on_progress=` 就必须同时出现 `with_progress=True`**。
以后新增调用点漏传会被立刻抓到。

## 4. Bug 3（状态变谎话）：中断后被留下的「进行中」状态

### 4.1 根因

`pipeline.run()` 的异常处理其实很完整：

```python
except Cancelled:      _mark(task_id, STATUS_CANCELLED)   # 取消不写 ERROR
except BaseException:  _mark(task_id, STATUS_ERROR)
```

**但进程被强杀 / 卡死后手动结束 / 断电时，这些 except 根本来不及跑。**
于是状态永远停在 `transcribing` / `roughing` / `refining` / `exporting`
——而实际什么都没在跑。用户下次打开看到「转录中」不动，只能一头雾水。

### 4.2 ★ 同样，风险早就写在代码里

`MainWindow.closeEvent` 的注释：

> "进程被强杀会留下「状态是 refining 但实际没在跑」的任务，
>  用户下次打开看到那个状态会一头雾水。"

**知道风险，但一直没做恢复。**

### 4.3 修法

新增 `store.reset_stale_inflight_statuses()`，在 `__main__` 启动时调用：

- 依据**数据**回退（不是时间戳）：有切片段 → `ready`（待导出）；否则 → `imported`（已导入）
- **不动** `error` / `cancelled` / `screened` 等稳定状态 —— 真错误要保留，不能被"自愈"抹掉
- 回退**安全**：`status` 全程只被写、**从不参与控制流**；转录缓存是按**文件**判断的
  ⇒ 不会重跑、不会丢缓存
- 清理失败不影响启动（状态只是记账）

## 6. 这件事说明了什么

三个 bug 里有**两个**是同一种形状：

> **同一类修复做过多次，却漏了其中一处；而漏掉的那处失败是静默的。**

- 管道死锁：`editor.py` 修过，`asr.py` 漏了
- 进度接线：6 处传了 `with_progress=True`，`clips_page` 漏了

而且两个都是**"只有在特定路径/特定素材上才暴露"**：

| Bug | 为什么之前的验证盖不住 |
|---|---|
| 管道死锁 | 取决于**素材静音段多少**，测试素材不够多就没触发 |
| 进度接线 | 取决于**走队列还是手动单条**，自动化测试走的是队列 |
| 残留状态 | 取决于**进程有没有被强杀**，正常退出不会发生 |

**⇒ 验收的覆盖面（走哪条路径、用什么素材）比断言的数量更重要。**
这三条都被 100+ 项自测和一次干净虚拟机验证漏过去了，
因为它们**验的不是用户实际走的那条路**。
