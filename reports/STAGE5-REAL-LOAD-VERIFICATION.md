## 3. ⚠️ 意外发现：时间线起始时间码（R20 需重新评估）

### 3.1 观察到的矛盾

`Sm2Sequence.MediaExtents` 解码后是 `[起始偏移秒, 时间线总长秒]`：

| 项目 | 项目帧率 | 起始偏移 | 总长 | 用过 OTIO？ |
|---|---|---|---|---|
| 新建项目 1（9-26） | 24 | **3600.0**（1 小时） | 38.625 | ❌ 用户自己拖的 dji 视频 |
| 新建项目 2（今天 15:24） | 30 | **0.0** | 60.0 | ✅ |
| 新建项目 3（今天 21:12） | 24 | **3600.0**（1 小时） | 135.0 | ✅ |

对应地，首个片段的 `Start`：项目 2 是 `0`，项目 3 是 `86400` 帧（=3600s@24fps）。

**两份 OTIO 都写了 `global_start_time = 0.0`**（已逐字节确认），但落点不同。

### 3.2 ✅ 定论：H2 成立（用户回答后）

先补一个关键事实：两份 OTIO 的 **rate 与目标项目帧率的关系不同**。

| 项目 | 项目帧率 | OTIO `global_start_time` | **rate 是否匹配项目** | 起始偏移 | 手动改过起始 TC？ |
|---|---|---|---|---|---|
| 新建项目 2 | 30 | `0.0/30.0` | ✅ 匹配 | **0** | **用户确认：没改过** |
| 新建项目 3 | 24 | `0.0/20.0` | ❌ 不匹配（20≠24） | **3600** | 没改过 |
| 新建项目 1 | 24 | （无 OTIO） | — | **3600** | — |

当时有两种自洽解释：**H1 项目属性论**（OTIO 不参与）与
**H2 rate 匹配论**（只在 rate == 项目帧率时生效）。

区分它们只需要一个我拿不到、但用户知道的信息：**项目 2 的起始时间码是不是手动设的**。

**用户回答：没有改过。**

⇒ **H1 被否证** —— 若起始 TC 纯由项目决定，项目 2 也该是 `01:00:00:00`，但它是 0。
⇒ **H2 成立**：

> **达芬奇确实会读取并采用 OTIO 的 `global_start_time`，
> 但前提是 OTIO 的 `rate` 与达芬奇项目帧率一致。**
> 不一致时，它**丢弃**该字段、回退到项目自己的起始时间码（新建项目默认 `01:00:00:00`）。

⇒ **TECH-DESIGN §6.3.3 的原结论方向是对的，只是漏了这个前提条件。**
（样本 E 那次之所以看到 `00:00:00:00`，很可能是"素材帧率 == 项目帧率"的巧合。）

### 3.3 解法（已写进 `导入说明.txt`）

| # | 做法 | 说明 |
|---|------|------|
| **① 首选** | 新建项目时把**项目/时间线帧率设为素材帧率** | rate 匹配 ⇒ 该字段生效 ⇒ 起点 `00:00:00:00`，字幕零摩擦对位 |
| **② 兜底** | 「项目设置 → 主设置 → 时间线起始时间码」改成 `00:00:00:00` | 覆盖"项目已建好、帧率改不了"的场景 |

❌ **不能靠改 OTIO 的 `rate` 去凑达芬奇的默认帧率** ——
`rate` 必须写素材真实帧率，否则切点的帧↔秒换算会整体错
（本次 ×1.2 重采样精确到 <1 帧，前提正是 rate 写对了）。写错会让**时长和位置全错**，
比时间码问题严重得多。

### 3.4 关于"我上一轮说它被推翻"

第一轮我写的是"该结论不再被数据支持"。**当时那样写是对的** ——
因为两个项目之间**不止"有没有 OTIO"一个变量，还差了 rate 匹配度**，
H1 和 H2 都自洽，而我手上没有能区分它们的数据。

**教训**（已写进项目长期笔记）：
碰上两种都自洽的解释，**先去找能区分它们的人或实验，而不是挑一个写进文档**。
这次只需问你一句话就定了。中间那版"两种假设并存"的写法虽然啰嗦，
但正是因为它没有被我一句武断的话盖掉，才留住了后来被证实的那个分支。

**用户报告**："达芬奇 otio 文件拖进去没有音频"。

### 6.1 根因

`exporter.export_davinci()` **只创建了一条 Video 轨**：

```python
track = otio.schema.Track(name="SliceQ_主轨", kind=otio.schema.TrackKind.Video)
...
timeline.tracks.append(track)      # ← 只有这一条
```

达芬奇导入后会**自己建一条音频轨，但那条轨是空的**，且**不会**从视频片段里
推断出音频。项目库证据：

```
新建项目 3（导入后）
  Sm2TiTrack  Type=0 name='SliceQ_主轨'  -> 3 个片段   ← 视频
  Sm2TiTrack  Type=1 name=None           -> 0 个片段   ← 音频【空】
  Sm2TiTrack  Type=2 name=None           -> 32 个片段  ← 字幕（用户后导入的 SRT）
```

**这不是实现 bug，是设计遗漏** —— TASKS.md 里甲方案的数据结构原文就是
「1 Timeline → **1 Video Track** → N Clips」，从头就没打算给音频。
所以阶段 5 的所有自测（73 项）**一条都没覆盖它**。

> ★ **教训**：验收清单只检查了"画面在不在"，
> 没有一条检查"声音在不在"。这是**验收维度本身的缺失**，比代码错误更难发现
> —— 因为自测全绿、日志无错、媒体在线，一切指标都"正常"。

### 6.2 修复

在 OTIO 里追加一条 `kind=Audio` 的轨，切点与视频轨**逐段一致**：

```python
track_v = otio.schema.Track(name="SliceQ_主轨",   kind=TrackKind.Video)
track_a = otio.schema.Track(name="SliceQ_主音轨", kind=TrackKind.Audio)   # ★ 新增

for i, h in enumerate(highlights, 1):
    seg_dur = RationalTime(h.duration * rate, rate)
    for tr in (track_v, track_a):          # ← 两条轨各建独立 Clip
        ref  = ExternalReference(target_url=src_url, available_range=...)
        clip = Clip(name=f"{i}_{h.title}", media_reference=ref,
                    source_range=TimeRange(start_time=..., duration=seg_dur))
        tr.append(clip)

timeline.tracks.append(track_v)
timeline.tracks.append(track_a)
```

⚠️ **必须各建独立的 `Clip` 对象**：同一个对象 append 到两条轨会互相覆盖
`range_in_parent`，表现为某条轨片段位置错乱，**且不报错**。自测里有专门一条守它。

### 6.3 自测（新增 10 项，73 → 83 项全过）

守命门的几条：

- 时间线**有 2 条轨**（Video + Audio）
- **音频轨片段数 == 视频轨片段数**（少一条就没声音）
- 音频轨逐段的「时间线位置 + 源内起点 + 时长」与视频轨一致
- **音视频是不同的 Clip 对象**
- 音频轨引用同一个源文件、每段都带 `available_range`
- 导入说明里含新增的两节（起始时间码 / 字幕导入方式）

## 7. 🔴 SRT 直接拖进达芬奇会整体提前 0.54 秒

用户已把 `规模验证_20260927_1851.srt` 导入「新建项目 3」。
我逐条比对达芬奇字幕轨的 `Start`（帧）与 SRT 文件：

| 时间线时间（达芬奇，已扣起始 TC 86400 帧） | SRT 时间 | 差 |
|---|---|---|
| 0.000s | 0.543s | −0.543 |
| 5.083s | 5.608s | −0.525 |
| 8.917s | 9.448s | −0.531 |
| 13.375s | 13.903s | −0.528 |

**32 条全部偏移，偏差恒定为 13 帧（0.542s）≈ 首条字幕的起始时间（0.543s）。**

**根因**：拖拽 / 顺序插入时，达芬奇**从时间线第 0 帧开始依次排列**，
因此**丢掉了第一条字幕的起始偏移**。后续条目按间隔排列，所以偏差恒定。

⚠️ **这不是 R20** —— R20 的表现是"偏 1 小时"，这里是亚秒级。
这个差别恰恰说明：**达芬奇的对齐基准是对的**（它确实按时间线起点对齐），
问题只在**插入方式**。

**⇒ 处理**（已写进 `导入说明.txt`）：
- ✅ `File > Import > Subtitle...` + 字幕轨右键
  **Insert Selected Subtitles to Timeline Using Timecode**
- ❌ 不要直接把 `.srt` 拖到时间线上

⏳ **待复验**：改用"按时间码插入"后是否零偏移。

## 8. 附：本次取证方法（可复用）

对 GUI 目标软件的产物验收，"用户看着正常"是**必要但不足**的证据。可复用的取证路径：

| 取证点 | 位置 |
|---|---|
| 剪映是否接纳外部草稿 | `%LOCALAPPDATA%\JianyingPro\User Data\Log\draft_acion_watch.json` → `suc` / `type` |
| 剪映草稿真实结构 | `<草稿>/draft_content.json`（片段 `target/source_timerange`、`materials.texts`） |
| 剪映是否真处理过 | 草稿目录文件 **mtime**（晚于导出时间 = 打开并重存过）+ `draft_content.json.bak` |
| 达芬奇是否导入 | `davinci_resolve.log` 搜 `Import Log`；**注意该日志是 GBK 编码** |
| 达芬奇媒体是否在线 | `Project.db` → `Sm2MpMedia`（条目数）、`Sm2TiItem.MediaFilePath` |
| 达芬奇切点/时长 | `Project.db` → `Sm2TiItem.Start/Duration/In`；`Sm2Sequence.FrameRate`、`MediaExtents` |
| 达芬奇离线情况 | `davinci_resolve.log` 搜 `offline` / `missing media` |

⚠️ 两个编码/语法坑：
- `davinci_resolve.log` 是 **GBK**，按 UTF-8 读会得到满屏 `????`；
- `Sm2TiItem` 的 `In` 是 SQL 关键字，查询**必须加双引号**，否则 `syntax error`。
