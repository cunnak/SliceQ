## 2. 前置实测：三个不确定点

### 2.1 R26 `drawtext` 段错误 —— 关闭，且确认不可修

```
rc = 3221225477 (0xC0000005 Access Violation)
崩溃前一行：Fontconfig error: Cannot load default config file
```

试过的三条修复路径**全部无效**：

| 尝试 | 结果 |
|---|---|
| 自建 `fonts.conf`（3 种写法：带/不带 DOCTYPE、带 `<config/>`） | 仍 0xC0000005 |
| `FONTCONFIG_FILE` 指向上面的文件 | 无效 |
| `FONTCONFIG_PATH` + `FONTCONFIG_DEBUG=1` | **零调试输出** |

`FONTCONFIG_DEBUG=1` 完全没有输出，说明这个 ffmpeg 构建里的 fontconfig
**压根不读环境变量** —— 属构建级缺陷，用户端无法修复。

**决策**：封面改走 **libass**。这个选择还有额外好处：
渲染链路与字幕**完全一致**，所以"样式预览所见即导出所得"这条原则自动成立
（TECH-DESIGN §4.6.4 明确要求预览走真渲染链路）。

### 2.2 libass 的字体到底生效不生效 —— 生效

同一句中文、同一画布，分别用三个字体渲染，比 MD5：

| 对比 | 结果 |
|---|---|
| SimHei vs SimSun | MD5 `20806c3104eb` vs `db8d7824400f` ⇒ **不同** |
| Microsoft YaHei vs SimHei | MD5 `d9e0ad5f713a` vs `fe8849f16e43` ⇒ **不同** |

⇒ libass **不依赖 fontconfig** 也能匹配到系统字体（走的是自己的 Windows 枚举），
**不存在"静默 fallback 到内建字体"的问题**。阶段 3 的字幕系统是可信的。

> ⚠️ **同时作废一条旧结论**：早期用 `ffmpeg -list_fonts` 测出"本机 0 个中文字体"，
> 并据此怀疑字体链路。实测该选项在本构建上**根本不存在**
> （`Error splitting the argument list: Option not found`），
> 我的解析代码把 stderr 当 stdout 读了，于是"解析出 0 个"。
> **教训：一个测量返回 0，先确认量具本身能用。**

### 2.3 `xfade` 与乙方案的结构性冲突

TASKS.md 阶段 4 第 1 项写的是"片段间 xfade 0.5s"，
但阶段 3 已定 **乙方案 = 每条候选一个独立 mp4** ——
**独立文件之间不存在"相邻片段"，`xfade` 无从施展**。

实测补充：`xfade` 还要求两路输入的**分辨率/像素格式/帧率完全一致**，
不一致时直接 `Conversion failed!`（错误信息不告诉你"是尺寸不匹配"）。

**决策**：淡入淡出重新定义为**单条片段自己的首尾 fade**（`fade`/`afade`）。
这既符合乙方案的产出形态，也是短视频实际需要的效果。
`xfade` 保留给未来可能的"合集模式"（同一源片切出的片段尺寸必然一致，风险可控）。

## 3. 交付物

### 3.1 新增 `sliceq/enhance.py`

| 功能 | 实现要点 |
|---|---|
| BGM 曲库 | `%APPDATA%/SliceQ/bgm/`，用户自备；`resolve_bgm()` 支持文件名/绝对路径/省略扩展名 |
| 单文件淡入淡出 | `video_chain()`：**先烧字幕再 fade**（否则片尾画面黑了字幕还亮着） |
| 配乐 ducking | `audio_filter_complex()`：`sidechaincompress` + `amix`，三种形态（原声+BGM / 仅 BGM / 仅原声） |
| 封面 | `pick_best_frame()` + `build_cover_ass()` + libass 渲染，1280×720 jpg |
| 「让位强度」四档 | `DUCK_LEVELS`：把 threshold/ratio 翻译成用户看得懂的档位 |

### 3.2 关键设计决策

**① 增强与切片在同一次编码里完成，不做"先切后增强"两步走。**
两步走会让画面多编码一代、无谓损失画质。代价是必须改用 `-filter_complex`
（`-vf` 与 `-filter_complex` 不能同时用）。

**② 默认全部「不做」。** 增强是显式加法 ——
片尾淡出 0.5s 虽然好看，但若作为默认值，老用户重导出时会发现画面莫名多出黑场。
GUI 自测专门断言了这一点（`opts.is_noop()` 必须为 True）。

**③ 找不到 BGM 要说话，不能静默降级。** 说了要配乐却找不到文件时，
在该条的 `notes` 里写明，并出现在导出清单和完成提示里。

**④ 不带 `sine` 滤镜当测试信号**（见 §4）。

## 4. 本轮最重要的一条：合成信号的标定不能迁移

### 4.1 问题的两次暴露

**第一次**：合成信号（440Hz 正弦）上标定出"有效"参数 `thr=0.05`。
搬到真实直播素材上，BGM 被压掉 **23.8dB**，而且**全程咬着不放**
（人声最弱的那 20% 窗口也压 22dB）。
原因：真实人声中位 **-11.9dB（线性≈0.25）**，`thr=0.05` 远低于它，任何时刻都远超阈值。

**第二次**：改用真实人声电平去扫参数，得到 `thr=0.2`。
但自测（合成素材）里 `thr=0.2` **完全不触发**（0.00dB）。
查下去才发现根因：

```
ffmpeg 的 sine 滤镜默认振幅是 0.125（-18dBFS），不是满刻度。
    裸 sine          峰值 -18.06dB   线性 0.125
    真实直播人声      峰值  -0.74dB   线性 0.92    ← 差 7.4 倍（18dB）
```

**我一直在用一个比真实人声轻 18dB 的信号标定压缩器阈值。**

### 4.2 正确的做法：受控实验

真实素材上找不到"静音段"（未明子直播全程有声，`silencedetect` 各阈值都抓不到），
所以**人工构造**两头明确的素材：

```
第 1 段（0~15s）  真实直播人声        ← 应该压
第 2 段（15~30s） 纯静音（anullsrc）   ← 应该恢复
```

再**单独输出 BGM 轨**（`bgm_raw` / `bgm_ducked`）——
两条轨都不含人声，电平差就是纯粹的压缩量。
（踩坑记录：`[bgm]` 被 `sidechaincompress` 消费后**不能再作输出**，
必须 `asplit` 分流，否则报
`Output with label 'bgm' does not exist in any defined filter graph`。）

### 4.3 标定结果

真实人声 RMS -14.2dB / 峰值 -0.56dB ⇒ 峰值线性幅度 ≈ 0.94

| threshold | ratio | 人声段压低 | **静音段压低** | 判定 |
|---|---|---|---|---|
| 0.05 | 8 | 15.40 dB | 0.00 dB | 过强 |
| 0.10 | 8 | 10.20 dB | 0.00 dB | 强 |
| **0.20** | **8** | **5.00 dB** | **0.00 dB** | **★ 默认** |
| 0.30 | 8 | 2.30 dB | 0.00 dB | 轻 |
| 0.50 | 8 | 0.60 dB | 0.00 dB | 太弱 |
| 0.20 | 4 | 4.30 dB | 0.00 dB | 轻 |

**「静音段压低」这一列才是真正的验收指标** ——
它恒为 0.00dB，说明压缩器在没人声时**完全恢复**，
即它确实在跟随人声，而不是一直压着不放。
只测"人声段压了多少"是不够的：参数过敏（一直压）同样能让那一列很好看。

> `level_sc`（sidechain 增益）在真实素材上**不需要**，默认 1.0 关闭。
> 合成信号"需要"它，只是因为正弦本身不真实。

### 4.4 沉淀成规则

> **测试素材的电平必须与真实素材对齐，否则标定出来的参数是错的。**
> 用 `sine` 造信号时记得它默认只有 -18dBFS；
> 需要特定幅度就用 `aevalsrc=exprs=0.9*sin(2*PI*f*t)`。

## 5. 本轮抓到的缺陷

### 5.1 产品缺陷（2 个，都已修）

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | **界面承诺的 SRT 不给** | 「不烧字幕：会另外导出一个 .srt 字幕文件」——但代码把 SRT 生成绑在 `burn_subtitles` 上，不烧就没有。用户按提示去找文件，根本不存在 | SRT 生成改为**只看有没有转录数据**，与烧不烧字幕解耦 |
| 2 | **导出结束冲掉业务层禁用** | `_set_running(False)` 无条件 `setEnabled(True)`，把"这个任务没有转录文本 → 不能烧字幕"的禁用一起打开 | 引入 `_running` + `_burn_available` 两个来源，统一由 `_sync_enabled()` 刷新 |

> 第 2 个是"改了 A 却坏了 B"的又一例：运行时状态的恢复逻辑
> 覆盖了业务规则的禁用状态。**两者必须分开记。**

顺带修掉一个同源问题：`_update_summary()` 里设的"无转录文本"警告，
会被紧接着调用的 `_on_mode_changed()` 覆盖成"不烧字幕：会另外导出 .srt"这种
常规提示 —— **真正的问题一个字都看不到**。现在警告优先级最高、直接 return。

### 5.2 我自己犯的错（4 个，比产品缺陷更值得记）

| # | 错 | 性质 |
|---|---|---|
| 1 | `-loglevel error` 把 `volumedetect` 的输出屏蔽了 | **量具坏了**。它是 `AV_LOG_INFO` 级，压到 error 就什么都读不到，表现为"测量函数返回 None"，看起来像断言失败 |
| 2 | 用 `bandpass` 从混音里抠 BGM，但人声（300Hz）在 BGM（4kHz）频带的**滤波泄漏**淹没了 BGM | **判据设计错误**。bandpass 只有 ~12dB/倍频程滚降，人声到了正常音量就漏得比 BGM 还响（实测把 -28dB 的 BGM 抬到 -18.8dB）|
| 3 | 旧版用 BGM=220Hz / 人声=440Hz，只差一个倍频程 | 同上，泄漏更严重 |
| 4 | 早期把 `ffmpeg -list_fonts` 的 stderr 当 stdout 解析 | **把"工具不存在"读成了"结果为空"** —— 差点据此怀疑整个字体链路 |

### 5.3 三次"期望写错"

| 期望 | 实际 | 结论 |
|---|---|---|
| 「切回精确模式后提示消失」 | 显示了"没烧字幕"的常规提示 | 测试没排除另一条提示 |
| 「烧字幕被禁用」 | 第 7 步的 `_set_running(False)` 把它重新启用了 | **这是真缺陷**（§5.1-2），测试抓对了 |
| 「整体电平抬升 ≥1dB」 | 只升 0.10dB | 人声主导总电平，BGM 叠上去本来就只抬这么多。**该测特征频率**（改测 880Hz 后 +5.30dB） |

### 7.2 素材层面的发现

抽帧选出的封面里**带有源视频自带的烧录字幕**（见验收报告附图）。
`pick_best_frame()` 现在只按"画面信息量"打分，不考虑"这个位置有没有字幕/UI"。
对自带字幕的录播，封面观感会打折。**可考虑**：选帧时避开底部 15% 区域评估，
或提供"手动换一帧"。

## 8. 附：一条该写进开发规范的检查项

> **凡是"参数需要标定"的地方，标定素材必须与真实素材在关键物理量上对齐
> （电平、采样率、声道数、语速…），并且要在真实素材上复核一次。**
>
> 本项目两次栽在这上面：第一次是幻觉率（拿没有内容的测试素材测出来"0 段幻觉"），
> 第二次就是 ducking（拿 -18dBFS 的正弦当人声）。共同点是
> **测试信号本身不具备被测量属性的真实分布**。
