## 三、根因

### 3.1 官方文档的直接答案

Blackmagic 官方《DaVinci Resolve 18.5 New Features Guide》原文：

> **There are two different OTIO formats supported by DaVinci Resolve:**
> - **`.otio`**: These files contain **just the metadata about the timeline and no associated media**.
>   They are small, portable, and **require the end user to link the timeline to their own copies of the media**.
> - **`.otioz`**: These bundle files contain **both the timeline metadata and all of the timeline's media assets**
>   zipped together into one file... it **assures that whoever imports the file has all the media needed and is
>   linked automatically**.
>
> **To Import:** If an `.otioz` file was selected, the media assets will unzip themselves into a folder at the same
> level as the `.otioz` file and **automatically link themselves**. **If an `.otio` file was selected, you will have
> to relink to your own copy of the media** if it's not in the same location as the original media.

**⇒ `.otio` 不自动链接媒体，是这个格式的定义行为。**

### 3.2 但仍有未解之处

官方说"若媒体在原始位置则无需重链接"。而我们的素材**确实在原始位置**，却仍然没链接。

这说明除了"格式本意"之外，**还存在 URL 写法层面的问题**——达芬奇可能根本没解析
`file:///C:/...` 这种 URL，或者解析后无法将其映射到媒体池。

第三方资料提供了旁证（Remotion 官方文档）：

> Do not leave an HTTP or HTTPS URL in `target_url`, or **reference media outside the .otio file's directory**.

> If any clips are offline, **relink them to the directory containing the .otio file**.

**⇒ 强烈暗示：达芬奇可能按"相对 `.otio` 所在目录"来解析媒体路径，而非使用绝对 URL。**

## 五、立即解法（不改文件，现在就能用）

三条路，按推荐顺序：

| # | 做法 | 说明 |
|---|------|------|
| **1** | 弹窗点 **「是」**，浏览到素材所在文件夹 | 达芬奇按**文件名**重新链接，一步解决 |
| **2** | 先取消导入 → 把 `source.mp4` **拖进媒体池** → 再导入 `.otio` | 媒体已在池中，链接成功率最高 |
| **3** | 导入后媒体池里选中离线片段 → 右键 `Relink Selected Clips` | 事后补救 |

> **关键认知**：这个弹窗**不是故障**，点「是」指到素材文件夹即可。
> 后续所有 OTIO 验证实验都可以这么做。

## 六、对 SliceQ 的产品影响（重要）

### 6.1 暴露了一个此前没想清楚的设计问题

**SliceQ 的 `.otio` 到底该引用什么素材？** 这决定了用户会不会每次都被弹窗拦一下。

| 方案 | OTIO 引用对象 | 优点 | 缺点 |
|------|--------------|------|------|
| **甲** | **原始源视频** + `source_range` 存切点 | 语义最正确，用户可任意调整切点 | 用户必须保留原片；跨机器必然要重链接 |
| **乙** | **SliceQ 自己切出的成片 MP4** | 交付包自包含，可能同目录自动链接 | 时间线上只有 1 个片段，"精修"意义弱 |
| **丙** | **每个高光切成独立 MP4**，OTIO 相对引用 | 自包含 + 可重排 + 可打 `.otioz` | 交付物变成"一堆小文件"，不再是单个 MP4 |

**当前实现走的是"甲"，且用了绝对 `file:///` URL——这正是最容易触发弹窗的组合。**

### 6.2 `.otio` vs `.otioz` 的取舍

| | `.otio` | `.otioz` |
|---|---------|----------|
| 含媒体 | ✗ | ✓（压缩打包） |
| 自动链接 | ✗ 需手动 | ✓ |
| 体积 | 几 KB | ≈ 全部素材体积 |
| 适合 SliceQ？ | 若引用原片 → 原片可能几个 GB | 若引用自己切的小片段 → **可行且体积可控** |

**⇒ 方案丙 + `.otioz` 是一个值得评估的组合**：自包含、自动链接、体积小、可重排。

### 6.3 需要用户决策的问题

1. **OTIO 引用原片还是引用 SliceQ 切的片段？**
2. **是否接受"交付包从单个 MP4 变成 MP4 + 若干片段文件"的形态变化？**
3. **是否把 `.otioz` 列为可选导出格式？**

> 这三个问题不阻塞阶段 1（应用骨架），但**影响导出的数据结构设计**，
> 最好在进入阶段 4（草稿导出）之前定下来。

## 八、v1 实验实测结果（2026-09-25 用户执行）

### 8.1 用户反馈

> 「实测了，两个样本都能够导入进去」

**结论：导入确实成功，且媒体是链接上的**——这一点此前被误判过，见 §8.3。

### 8.2 ⚠️ 项目库证据揭示的问题：分布不符预期

从项目库 `新建项目 1` 中查到：

```
Sm2Timeline            = 9 条   (A / E / B / F / V4 / V5 / V1 / V3 / V2)
Sm2TiItem              = 27 条  (9 × 3 片段)  ← 片段都在

按媒体路径聚合：
  test_media\source.mp4        21 项  = 7 条时间线
  media_link_test\source.mp4    6 项  = 2 条时间线
  合计 27 项 / 9 条时间线 ✓
```

**每个片段都有 `MediaFilePath`（真实 Windows 路径）与 `MediaRef`**
⇒ **媒体确实链接成功，时间线不是离线的。**

**但分布是 7 : 2，而不是预期的 4 : 5。**

- 预期：A/B/E/F（4 条）→ `test_media`；V1~V5（5 条）→ `media_link_test`
- 实际：7 条 → `test_media`，2 条 → `media_link_test`

**多出的 3 条只可能是 V3 / V4 / V5。**

**推断（强提示）**：达芬奇在**无法解析 `target_url`** 时，会**退回"按文件名在媒体池里找"**。
由于 v1 实验的 5 个样本**文件名全是 `source.mp4`**，
V3/V4/V5 的路径解析失败后，命中了池中更早的同名文件（`test_media` 那份）。

**倾向性结论**：
- **V1 `file:///C:/...`** → 解析成功 ✅（**我们当前实现用的就是这个**）
- **V2 `file://localhost/C:/...`** → 解析成功 ✅
- **V3 `C:/...` / V4 `C:\...` / V5 相对路径** → **解析失败** ❌，退回文件名匹配

> ⚠️ 该结论**尚不能定论**，见 §8.4。

### 8.3 本次自我纠错记录（两次）

**第一次**：曾根据 `MediaPool::MpVideoClip` 表为 0 行，判定"媒体池是空的、媒体全离线"。
**错**——该表已废弃，真正在用的是 `Sm2MpMedia`（11 行，含 2 个 `Sm2MpVideoClip`）。

**第二次**：用 shell 循环批量 `COUNT(*)` 时把 stderr 重定向到 `/dev/null`，
导致查询失败的输出是**空白**而非 0，几乎据此下了错误结论。

> **教训**：① 数据库表名要先确认哪个在用，不要凭表名猜；
> ② **批量查询不要吞 stderr**——空白与 0 是两回事。

### 8.4 v1 实验的设计缺陷（我自己的错）

**5 个样本引用同一个文件名 `source.mp4`，只改路径写法。**

这导致**"路径被解析成功"与"按文件名蒙对"在结果上无法区分**——
两者都会显示"媒体已链接"，但语义完全不同。

### 8.5 修正实验：阶段 0.8-B（洁净版，已生成）

位置：`stage0/test_drafts/media_link_test2/`
脚本：`probe_resolve/gen_media_link_variants2.py`

**每个变体引用独一无二的媒体文件名**：

| 样本 | 媒体文件 | target_url 写法 |
|------|---------|----------------|
| V1 | `media_V1.mp4` | `file:///C:/...` |
| V2 | `media_V2.mp4` | `file://localhost/C:/...` |
| V3 | `media_V3.mp4` | `C:/...`（纯路径·正斜杠） |
| V4 | `media_V4.mp4` | `C:\...`（纯路径·反斜杠） |

## 九、0.8-B 洁净实验结果（2026-09-25 20:03 实测）★ 定论

### 9.1 实测数据

用户在**全新项目**中导入 V1~V5。项目库查询结果：

**媒体池中的视频素材（5 个，各自唯一）**：

```
media_V1.mp4
media_V2.mp4
media_V3.mp4
media_V4.mp4
media_V5.mp4
```

**时间线项的媒体路径归属**：

| 时间线 | 链接到的媒体 | 项数 | 结果 |
|--------|-------------|------|------|
| V1 (`file:///C:/...`) | `media_V1.mp4` | 3 | ✅ |
| V2 (`file://localhost/C:/...`) | `media_V2.mp4` | 3 | ✅ |
| V3 (`C:/...` 纯路径正斜杠) | `media_V3.mp4` | 3 | ✅ |
| V4 (`C:\...` 纯路径反斜杠) | `media_V4.mp4` | 3 | ✅ |
| V5 (`media_V5.mp4` 相对路径) | `media_V5.mp4` | 3 | ✅ |

**每个时间线都正确链接到自己那个唯一的文件——零错配。**

### 9.2 结论：`target_url` 写法不是决定因素

**五种写法全部可用。** 此前怀疑"纯路径/相对路径解析失败"的推断**被证伪**。

**⇒ 我们当前实现的 `file:///C:/...` 是正确的，无需改动。**

### 9.3 但这同时反证了 v1 异常的真实原因

回顾 v1 实验的 **7 : 2** 异常（§8.2）：当时 5 个 V 样本引用的文件**全叫 `source.mp4`**，
结果有 3 条链到了 `test_media` 那份同名文件。

而 0.8-B 中文件名唯一 ⇒ **零错配**。

**⇒ 两者对照，指向同一机制（现已强化为实测支持）：**

> **达芬奇优先"按文件名"匹配媒体池中已有条目；
> 只有当池中没有同名文件时，才使用 `target_url` 声明的路径。**

这解释了两个实验的全部现象：
- v1：池中已有 `source.mp4`（test_media 那份）→ 部分样本被同名匹配走 → 错配
- 0.8-B：文件名唯一，池中无同名 → 全部按声明路径链接 → 零错配

**⇒ R23（同名静默错配）由"推断"升级为"实测支持的风险"。**

### 9.4 对设计的最终影响

| 项 | 决定 |
|---|---|
| `target_url` 写法 | **维持 `file:///C:/...`**（已验证可用，且是标准写法） |
| `.otio` 首次导入弹窗 | **仍需 `导入说明.txt`** —— 媒体不在池中时达芬奇仍会问 |
| **同名冲突** | **写入 `导入说明.txt`**：提醒用户媒体池中若已有同名文件，可能链到错误素材 |
| 甲方案 | **不变**（引用原始源视频 + `source_range`） |

### 9.5 追加提醒（写入导出说明的必要内容）

由于 R23 已成立，`导入说明.txt` 需增加一条：

```
■ 注意
   若你的媒体池中已有同名素材，达芬奇可能链接到那个同名文件
   而不是本包指定的源文件。导入后请确认时间线指向的是正确的素材。
```

## 十、阶段 0.7-v2 样本 E 实测结果（2026-09-25）★ 定论

### 10.1 结果

**用户实测：样本 E 导入后，时间线起始时间码 = `00:00:00:00`。**

（另有旁证：导入对话框中「时间线起始时间码」字段即显示 `00:00:00:00`，且为灰色不可编辑——
说明该值由 OTIO 内容自动派生。）

### 10.2 结论：时间码起点陷阱可以规避 ✅

**达芬奇会读取并采用 OTIO 中 `Timeline.global_start_time = 0` 的设定。**

因此 **R20（时间码起点陷阱）的解法①成立**：

> 只要 SliceQ 在导出的 OTIO 里显式写入 `global_start_time = 0`，
> 用户导入后时间线起点即为 0，**SRT 按时间码插入时不会偏移 1 小时**。

**⇒ R20 从"高"降级为"已可控"。**

### 10.3 仍保留的兜底

虽然解法①成立，**`导入说明.txt` 中仍保留手动设置时间线起点的步骤**——理由：
- 用户可能在**已存在的时间线**上加字幕（此时起点受原时间线影响）
- 用户可能不使用 OTIO，直接拖 SRT 进自己的项目

**双保险比单保险便宜。**

### 判读 Marker 的简明方法（供下次查看）

在达芬奇**编辑页**打开 `B_短Marker` 时间线，然后：

1. 看**时间线标尺上方**是否有**小三角/圆点标记**（青色）
2. 鼠标**悬停**在标记上 → 是否弹出文字「候选高光：开场包袱」
3. 若找不到：菜单 `时间线 > 显示标记`（或快捷键 `M`）切换显示

**有标记 + 显示名称** → Marker 通道可用
**无标记** → 高光说明改放 `Clip.name`

> Marker 结果**不阻塞阶段 1**，但影响阶段 4/5 的"高光说明"承载方式。
