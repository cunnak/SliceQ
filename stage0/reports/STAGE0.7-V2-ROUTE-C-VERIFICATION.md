## 二、查证结论（2026-09-24 联网核实）

### 2.1 ✅ 达芬奇免费版原生支持 SRT 导入

**证据来源**：多个独立教程站 + Blackmagic 官方《DaVinci Resolve 19 New Features Guide》

| 项目 | 结论 |
|------|------|
| 支持版本 | **免费版即有**（Studio 独有功能是"语音转字幕"，与 SRT 导入无关） |
| 操作路径 | `File > Import > Subtitle` 或 媒体池右键 → `Import Subtitle` |
| 精确对位 | 右键字幕剪辑 → `Insert Selected Subtitles to Timeline Using Timecode` |
| 快捷方式 | 直接把 SRT 拖到视频轨上方的灰色区域 → **自动创建字幕轨** |
| 支持格式 | SRT / WebVTT / IMSC |

**关键结论：SRT 是真兜底，不是假兜底。用户全程不需要手动对时间。**

### 2.2 ✅ OTIO 的 Marker 是一等公民

**证据来源**：OpenTimelineIO 官方《File Format Specification》

OTIO 的 `Clip` 与 `Track` 对象在文件格式规范中都**显式包含 `markers` 字段**：

```json
{
    "OTIO_SCHEMA": "Clip.1",
    "effects": [],
    "markers": [],        ← 原生支持
    "media_reference": null,
    ...
}
```

`Marker` schema 支持：`name`（文本）、`marked_range`（位置）、`color`（颜色枚举）。

**理论上，高光说明可以随 OTIO 完整传递。** 但**实际是否保留取决于达芬奇**——这正是 v2 样本 B 要测的。

### 2.3 ⚠️ 坑一：时间码起点陷阱（**会直接毁掉用户体验**）

**这是本轮查证最重要的发现，此前设计完全没考虑到。**

| 事实 | 说明 |
|------|------|
| 达芬奇默认时间线起点 | `01:00:00:00`（1 小时） |
| SRT 时间码 | **零基**（第一条字幕通常在 `00:00:01` 附近） |
| 冲突后果 | 按时间码插入字幕 → **全部偏移 1 小时** → 用户看不到字幕，以为功能坏了 |

**两个独立来源（cutconvert.com、creativevideotips.com）都专门为此写了警告章节**，说明这是高频踩坑。

**SliceQ 必须内建处理**，否则 C 路线的"SRT 兜底"会变成用户投诉源。三种候选解法：

| 解法 | 做法 | 评价 |
|------|------|------|
| ① OTIO 指定起始为 0 | 在 OTIO 里写 `global_start_time = 0`，看达芬奇是否跟随 | **v2 样本 E 正在测** |
| ② 文档提示手改 | 用户导入前手动把时间线起点设为 0 | 可行但把活儿推给用户 |
| ③ SRT 时间码偏移 1 小时 | 导出时给 SRT 所有时间码 +1h | 治标，换软件就错 |

### 2.4 ⚠️ 坑二：字幕轨 ≠ Text+ 标题（两种东西）

达芬奇里"字幕"有两条技术路线，**能力完全不同**：

| | 字幕轨（Subtitle Track） | Text+ 标题（Title） |
|---|---|---|
| 位置 | 视频轨上方的专用轨 | 视频轨上的片段 |
| 导入 SRT | ✅ 原生支持 | ❌ 不能 |
| 导出 SRT | ✅ 支持 | ❌ **导出按钮直接灰掉** |
| 逐条独立样式 | ❌ 只能整轨统一 | ✅ 每条可独立调 |
| 承载 FCPXML | 有限 | ✅ |

**对 SliceQ 的启示**：如果用户后期想要"每条字幕独立调样式"，我们需要能输出 **FCPXML 标题**，
而不只是 SRT。这是**未来可选增强**，不阻塞 v1。

## 三、v2 实验样本（已生成）

位置：`stage0/test_drafts/otio_matrix_v2/`

| 样本 | 文件 | 结构 | 测什么 |
|------|------|------|--------|
| **A** | `A_基准_无标记.otio` | 1 轨 / 3 片段 / 0 标记 | **对照组**（确认基准能力） |
| **B** | `B_短Marker.otio` | 1 轨 / 3 片段 / **3 标记** | ★ **Marker 是否保留** |
| **E** | `E_起始时间码为0.otio` | 同上，但显式指定起始=0 | ★ **时间码陷阱能否规避** |
| **F** | `F_长Marker_120字.otio` | 1 轨 / 3 片段 / **3 个长标记** | **长文本是否截断** |

**样本实际体积**：

```
A_基准_无标记.otio          7,668 bytes   （最短标记名 0 字）

E_起始时间码为0.otio        10,345 bytes   （最短标记名 9 字）
F_长Marker_120字.otio      11,188 bytes   （最长标记名 103 字）
```

> ⚠️ 注：样本 F 命名里的"120 字"是设计意图，**实际写入 103 个中文字符**。
> 不影响测试有效性（103 字已远超达芬奇可能保留的长度），但报告与结果应以此为准。

**样本生成脚本**：`probe_resolve/gen_otio_matrix_v2.py`

## 七、结论将如何影响设计

| 实验结果 | 含义 | 设计决策 |
|----------|------|---------|
| **B3 = 有** | Marker 可保留 | 高光说明走 Marker 通道，OTIO 价值确认 |
| **B3 = 无** | Marker 丢失 | 高光说明改放**片段名**（`Clip.name`），放弃 Marker |
| **E2 = 0** | 时间码可控制 | OTIO 直出即对齐，用户在达芬奇里导入 SRT 零摩擦 |
| **E2 = 1h** | 时间码不可控 | PRD 必须写明"导入前请将时间线起始时间码设为 0"，并提供一键偏移 SRT 工具 |
| **F2 = 截断** | 长文本不可用 | 高光摘要限长，完整说明写进随包 Markdown 或应用内查看 |

> 无论结果如何，本轮都会把"OTIO 能传什么"从**猜测**变成**确定的设计输入**。
