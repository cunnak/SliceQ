## 一、背景（为什么要做这一步）

阶段 0.5-B 实测结论：**达芬奇脚本直连不可行**。证据链：

| # | 检查项 | 结果 | 排除的假设 |
|---|--------|------|-----------|
| 1 | `fusionscript.dll` PE 导入表 | 无任何 `python*.dll` | ~~Python ABI 版本不匹配~~ |
| 2 | 依赖 DLL（`lua5.1.dll` / `tbbmalloc.dll` / VC 运行库） | 全部存在于 `C:\davinci\` | ~~依赖缺失~~ |
| 3 | `os.add_dll_directory(r"C:\davinci")` | 无效，仍旧崩溃 | ~~DLL 搜索路径问题~~ |
| 4 | `faulthandler` 捕获 | `0xC0000005` 访问冲突，崩在 `create_module` | 崩点在原生 `DllMain` |
| 5 | 导出表分析 | 含 `Py3ScriptLanguage` / `Py2ScriptState` 等类 | DLL 内嵌脚本引擎，反向驱动 Python |

**根因**：`fusionscript.dll` 在被 `LoadLibraryEx` 映射的瞬间（`DllMain` 内）执行了非法操作，触发原生访问冲突。**该崩溃不可被 Python 捕获**（连 `faulthandler` 都只能说"access violation"，拿不到 Python 栈）。

**决策**：不修。理由不是修不好，而是——即使在本机修好，这个 DLL 对**安装路径、Python 环境、VC 运行时版本**极度敏感，而 SliceQ 要分发给多个切片 man，他们的达芬奇可能装在 D/E 盘、可能是 Studio 版或 19.x。**把直连做成内置能力 = 把不可预测的环境故障转嫁给每个用户。**

**替代方案**：导出 **FCP7 XML**（`xmeml v4`），用户手动导入。零依赖、跨版本、无需配置。

## 二、产物文件

| 文件 | 说明 |
|------|------|
| `SliceQ_Stage0_Test.original.xml` | 阶段 0 原始产物（**备份，含已知缺陷**） |
| `SliceQ_Stage0_Test.davinci.xml` | **本次验收用** — 已修补两处缺陷 |
| `../../test_media/source.mp4` | 素材（1280x720 / 30fps / h264+aac / 12.0s / 360帧） |

### 已修补的两处缺陷

**DEFECT-1 — `<rate>` 重复**
原 XML 每个 `<clipitem>` 内出现**两个完全相同的 `<rate>` 块**（OTIO fcp adapter 输出怪癖）。部分 FCP7 解析器会因此报错。已折叠 3 处。

**DEFECT-2 — `<format/>` 为空**
原 XML 的 `<format/>` 是自闭合空标签，达芬奇无法据此推断序列规格。已替换为完整规格块：

```
width=1280, height=720, anamorphic=FALSE, pixelaspectratio=square
fielddominance=none, rate=30 NDF
audio: depth=16, samplerate=48000, channelcount=2
```

> ⚠️ 注意：`<format>` 修的是**序列规格**，不是修复时间线内容。时间线内容（3 个 clipitem）原本就是对的。

## 五、如果失败怎么办

| 失败现象 | 可能原因 | 下一步 |
|----------|----------|--------|
| 导入报 XML 解析错误 | 达芬奇对 `xmeml` 版本挑剔 | 尝试 `otio` 原生格式，或改导 EDL |
| 时间线创建但片段全离线 | `pathurl` 路径格式不被接受 | 改用相对路径 / 先手动导入素材再导时间线 |
| 片段数不对（多/少） | OTIO 适配器丢帧或重复 | 回到 OTIO 层排查，而非 XML 层 |
| 达芬奇崩溃 | 素材编码不支持 | 换 ProRes 测试素材复现 |

> **重要**：无论成功或失败，结果都是有效数据。失败同样要记录——它决定了阶段 3 交付形态的最终设计。
