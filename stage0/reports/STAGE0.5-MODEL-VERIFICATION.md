## 2. R12 音轨理解 —— ✅ 彻底解决

### 测试设计

用 FFmpeg 的 `flite` 滤镜合成英文语音（**避免用真实人声素材，确保测试内容完全可控**）：

```
ffmpeg -f lavfi -i "flite=text='Slice Q audio test. The secret number is seven four two one.':voice=slt"
```

再用本地 whisper 校验语音内容无误（转录得 `"Slice Q audio test, the secret number is... 7-4-1"`，tiny 模型精度有限但确认了主要内容），最后封装成带 `testsrc2` 画面的 651KB 小视频。

### 结果

**T1 — 只问音轨**：

> **问**：这个视频里的语音（人声）说了什么？请逐字复述，特别是数字。
>
> **答**：视频里的人声（英文合成语音）说的是：
> "Slice Q audio test. The secret number is seven four two one."
> 其中提到的数字是 **7421**

**T6 — 只问画面，看它是否主动报告音频**：

> **答**（在描述完彩条、时间码、像素方块等画面细节后，附带）：
> - **音频**：一个合成女声说："Slice Q audio test. The secret number is 7421."

**双重确认：模型对音轨是主动、完整、跨模态联合处理的。**

### 结论

彻底推翻了 VL 系列文档里"不支持对视频文件的音频进行理解"的限制——**该限制不适用于 omni 系列**。

**这直接决定了两件事**：
1. TECH-DESIGN §9 的 **R12 风险关闭**（原等级"中"）
2. 粗筛/精析阶段可以用音量突增、情绪爆发、语速突变等**纯音频信号**做高光判定——娱乐/聊天类内容的核心判据保住了

**附带发现：模型的画面理解精度相当高。** 对 `testsrc2` 测试图案，它准确描述了彩条的六色顺序、时间码从 `00:00:00.500` 递增、第 2 秒出现的灰色竖条、甚至"像是信号干扰或渲染伪影"这类判断。对游戏击杀/操作识别的能力可以乐观预期。

## 3. 视频输入方式 —— 架构级修正

### 实测矩阵

| 测试 | 传参方式 | 结果 | 证据 |
|---|---|---|---|
| T1 | base64 data URI (`data:video/mp4;base64,…`) | ✅ **200** | prompt_tokens=1005 |
| **T2** | **`file:///C:/…` 本地路径** | ❌ **400** | `InternalError.Algo.InvalidParameter: The provided URL does not appear to be valid.` |
| **T3** | **`C:\…` Windows 路径** | ❌ **400** | 同上 |
| T4 | 公网 URL | ✅ **200** | prompt_tokens=3746 |

### 这否定了 TECH-DESIGN v1.2 的 §3.1

v1.2 写的是：

> **SDK：必须使用 DashScope 官方 SDK（`dashscope` pip 包），不是 OpenAI 兼容端点。**
> …精析级的输入正是本地切出的候选片段…**改用官方 SDK 后，本地路径直传，无需 OSS、无需公网 URL、无需上传环节。**

**这个判断成立的前提是走百炼官方端点。** 但当前用的是中转站——**中转站只有 OpenAI 兼容 HTTP 接口，服务端物理上无法访问用户磁盘**，本地路径传参不可能成立。这不是配置问题，是拓扑问题。

### 修正后的结论

本地路径直传是 **DashScope 官方 SDK 独有能力**，不是协议能力。因此架构必须按"两种 transport"设计：

| Transport | 视频输入 | 体积上限 | 需要 |
|---|---|---|---|
| **官方 DashScope SDK** | ✅ 本地路径直传 / base64 | 本地路径 ≤100MB | 阿里云百炼账号 |
| **OpenAI 兼容 HTTP（中转站）** | ❌ 无本地路径；✅ base64 / 公网 URL | **base64 ≤ 28,000,000 字符（原始 ~20MB）** | 中转站 key |

**这在架构含义上不是小事**：
- 走官方 SDK → 精析副本可以很大（几分钟一段随意切），转输环节最少
- 走中转站 → 副本必须压到 ~15MB 以内，**这反过来约束了"候选段粒度"与"副本码率"**

## 4. base64 体积上限 —— 撞到硬墙，拿到精确数字

### 阶梯实测

| 原始体积 | base64 体积 | HTTP | prompt_tokens | 耗时 |
|---|---|---|---|---|
| 1,125,296 B | 1.43 MB | ✅ 200 | 4,566 | 5.1s |
| 3,193,258 B | 4.06 MB | ✅ 200 | 6,836 | 8.2s |
| 5,249,435 B | 6.68 MB | ✅ 200 | 9,106 | 14.3s |
| 7,784,249 B | 9.90 MB | ✅ 200 | 11,376 | 10.7s |
| 10,834,421 B | 13.78 MB | ✅ 200 | 13,646 | 12.8s |
| 21,647,067 B | 27.53 MB | ❌ **400** | — | 63.2s |
| 36,017,208 B | 45.80 MB | ❌ **400** | — | 44.1s |

### 上限的精确来源

失败响应（这是最有价值的一条信息）：

```json
{"message": "String value length (28049408) exceeds the maximum allowed (28000000,
 from `StreamReadConstraints.getMaxStringLength()`)", "type": "invalid_request_error"}
```

**读法**：

- **硬上限 = 28,000,000 字符**（base64 字符串长度）
- 报错来自 **Java Jackson 的 `StreamReadConstraints`** —— 这是**中转站网关的反序列化保护**，**不是模型的限制**
- 换算：28,000,000 字符 ÷ 1.3333 ≈ **原始文件 20.99 MB**

**因此安全预算**：

| 项 | 数值 |
|---|---|
| base64 字符串硬上限 | 28,000,000 字符 |
| 对应原始文件理论上限 | ~20.99 MB |
| **建议工程上限（留 30% 余量）** | **原始 ≤ 15 MB / base64 ≤ 20 MB** |

> 注意：官方 DashScope 文档称 base64 单文件上限 **10MB 且原始须 <7MB**。实测该中转站**更宽松**（13.78MB base64 通过）。**不要用官方文档的 7MB 去做设计**——以实测为准。

## 5. 成本规律 —— 找到了干净的线性关系

### 关键数据

各档次的 prompt_tokens **只与视频时长相关，与文件体积无关**：

| 时长 | prompt_tokens | 比值 |
|---|---|---|
| 20 s | 4,566 | 228.3 /s |
| 30 s | 6,836 | 227.9 /s |
| 40 s | 9,106 | 227.7 /s |
| 50 s | 11,376 | 227.5 /s |
| 60 s | 13,646 | 227.4 /s |

**≈ 228 token / 秒视频**，五档一致，线性度极高。

### 推算 SliceQ 单条成本

条件：3 小时录像 → 粗筛后候选段 ≤20% = **36 分钟 = 2,160 秒**

| 环节 | 计算 | 成本 |
|---|---|---|
| 精析输入 | 2,160 s × 228 = **492,480 token** × ¥0.8/M | **¥0.39** |
| 精析输出（关思考） | 按 120s/段 = 18 次调用 × ~200 token = 3,600 × ¥2.7/M | ¥0.010 |
| 粗筛文本粗判 | 3h 转录约 4 万 token 分窗 | ¥0.03 ~ 0.10 |
| 断句/文案（纯文本） | 候选段字幕 | ≤ ¥0.05 |
| **合计** | | **≈ ¥0.45 ~ 0.55** |

**对照 PRD KR3（≤¥1）：宽裕达标，余量约一倍。**

> 若候选段实际占比低于 20%，成本还会进一步下降。

### 优化杠杆（已识别，待阶段 2 验证）

- 分析副本降 fps（如 15fps→5fps）可能减少模型采样帧数 → 直接压缩 token
- 关闭思考（`enable_thinking: false`）可省去 reasoning token 的开销与耗时

## 6. 思考 token 的实测分布

| 测试 | completion | reasoning | 正文占比 |
|---|---|---|---|
| T1（base64 + 问音轨） | 246 | 189 | 23% |
| T4（公网 URL + 问画面） | 861 | 578 | 33% |
| T6（base64 + 问画面） | 1,197 | 891 | 26% |
| T5（`enable_thinking:false`） | 2 | **0** | 100% |

**读法**：
- 默认开启思考时，**65%~75% 的输出预算被 reasoning 吃掉**，正文只剩四分之一
- `enable_thinking: false` 被该端点接受（HTTP 200），可完全关闭
- 本次测试 `max_tokens` 给得足（1500/400），未出现"正文为空"的空返回；但**若 max_tokens 设小，必然触发技能里描述的那个陷阱**（HTTP 200 + finish_reason=stop + 正文为空）

**实现要求（写进 TECH-DESIGN）**：

1. 精析阶段默认 `enable_thinking: false`（要的是结构化定位，不需长推理）
2. `max_tokens` 不得低于 800（给结构化 JSON 输出留余量）
3. 必须实现**空返回自检**：`正文为空 且 reasoning_tokens > 0` → 自动改 `enable_thinking:false` 重试一次，并把降级事件上报 UI
4. `enable_thinking` 参数须做成三态可配（`auto` 不发送 / `off` / `on`），遇 400/422 自动摘除重试
